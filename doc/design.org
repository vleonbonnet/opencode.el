* The server is authoritative

Buffers render what the service reports and keep only interface state: which blocks are expanded, the prompt being typed, pending answers. Agent, model, variant, status and transcript come from the service, so another client's actions show up in Emacs and nothing needs reconciling beyond what reconnection does.

* One service, one stream

OpenCode 2 runs one background service per user. Emacs never starts a server of its own and never stops the service: the TUI and the desktop app share it, and it resumes running turns after a restart. Every location's events arrive on a single =GET /api/event= stream. The process filter only splits frames and queues them, and a zero-delay timer dispatches them in time-bounded batches, because the service drops a subscriber that falls 4096 frames behind and a slow handler must not stall the socket. Frame scanning resumes where the previous chunk ended, so a multi-megabyte tool result costs linear time. Nothing is replayed after a reconnect: =server.connected= has every open buffer catch up with the service, writing only what it missed (see [[*Catching up after a reconnection][Catching up after a reconnection]]).

Locations are keyed by the exact directory string the service receives, so every directory is normalized the same way: truename, trailing slash, and an uppercase drive letter on Windows.

Whatever stops the service, Emacs restarting or stopping it, another client, a crash, the next request starts it again: a refused connection is retried once after =opencode-service-ensure= found or started a service. While Emacs runs =opencode service restart= or =stop=, requests wait for the CLI to end, then for a ready service, rather than reach the service going away or run =opencode service start= beside the CLI: every lookup is numbered, and a restart or stop numbers a new one, so that a lookup in flight, which may have found the service going away, settles nothing.

The stream must come back as soon as the service does, or replies stop rendering while prompts still go through. It reopens after a backoff when it ends, and at once, without backoff, whenever a service is ready for Emacs: after any start, restart or lookup Emacs made, such as the one following a request refused by a service that went away. One still open on another service process moves to the ready one. A sent prompt, command or shell command reopens it at once too, and the heartbeat watchdog reopens a wanted stream left closed with nothing reopening it, so that no lost notification leaves buffers stale. =opencode-service-stop= closes it and keeps it closed, since reopening it would start the service again; a service ready again reopens it only while session buffers are open or the registry has clients (=opencode-events-wanted-functions=). =opencode-disconnect= alone keeps it closed until a client connects.

The watchdog drops a stream that sent nothing, not even its heartbeat every 15 seconds, for =opencode-events-heartbeat-timeout= seconds. Emacs reads no output while the machine sleeps, nor while it is busy, so silence then is no evidence: dropping the stream on waking cost a healthy stream a reconnection, and every buffer a resynchronization. The watchdog checks every 15 seconds, and a check coming more than one interval late, or finding the clock set back, means it could not watch meanwhile: the silence then counts from that check, which gives the stream a whole timeout to deliver a heartbeat. A stream that died meanwhile is dropped once that timeout passed, as one dying while Emacs watches is. Comparing a check with the previous one rather than reading the timer's schedule also covers Emacs's catching up on a late repeating timer, which runs it several times in a row: only the first of them is late.

Every request, the stream included, goes through =opencode-transport-request=, which settles it exactly once, whatever ends it, and kills its connection's buffer with the connection (see [[*No process per request][No process per request]]). Requests went through curl and =plz= before, and =plz= calls back only on the curl exits it recognizes, worded as on GNU/Linux: on macOS, a curl process killed by a signal reported =killed: 9= and ended without a callback, which left buffers behind and streams never reopened, so a wrapper had to settle what =plz= did not.

A service starting on a database from OpenCode 1 imports that history in the background while it already answers, and it answers 404 for a session the import has yet to reach. So ready means imported: =opencode-service-ensure= polls =/api/experimental/migration/v1= once per service process before it settles its waiters, and no request can mistake a session not imported yet for a deleted one. A failed or stalled import is reported and then left behind, since the service is usable without it.

* One registry of session state

Session buffers know only their own session, so pickers and other packages' lists and dashboards read the registry in =opencode-state.el= instead: one entry per session, with its live state, independent of buffers. It holds what the service reports and derives the status from it; nothing is decided locally, so another client's actions show up and nothing needs reconciling beyond what a reconnection does.

Every time the stream connects, whoever opened it, the registry is rebuilt from REST: one page of the newest unarchived sessions, then the running ones, those older than the page fetched one by one, then the pending permission requests and forms of the running ones. The active list is fetched after the page, so a turn that ended in between shows as ended rather than running forever. Nothing is replayed after a reconnect, so events received before the requests are covered by their answers, and those received while they run are held and applied over the result. The registry is then ready and follows events. An event of a session whose entry is not current on this stream, unknown or left from the previous stream, fetches that session first, holding its events meanwhile.

The registry holds every unarchived session, not only the newest: lists such as drover's show the user's own sessions, and with many subagents, which are sessions too, a fixed number of the newest left out older top-level sessions still open in buffers. A service holds thousands (one had 2510 unarchived, 967 of them top-level), and one unpaged listing of them is 1.4 MB of JSON, so after the ready page the others are listed a page of 250 at a time, newest first, one request after the other, each page parsed and installed as it arrives: with Emacs 31's parser, a page costs about 0.6 ms to parse and as much to install, and allocates about 0.8 MB, so the main thread is never held for more than a page and a garbage collection. =session.list= has no maximum page size; its cursor anchors on the last session's update time and ID, and carries the first page's filters and order, so later pages send the cursor and the size alone. A session updated during the listing moves ahead of the first page, where later pages never find it; events the registry follows fetch such a session themselves, and for any other update the listing ends by following the first page's =previous= cursor, which lists the sessions newer than it. A page only installs the sessions the registry holds no current entry of: one an event fetched or changed since is newer, and one deleted meanwhile stays deleted. Sessions of a later page are not running, since the running ones came with the ready page, and only the failure of one whose failure is still unseen has its message fetched, the status showing it; so loading them all costs a request per page, not per session. A page that fails is asked again after a backoff, the registry staying ready. Clients hear of each page once: =opencode-state-updated-functions= runs once per batch, with nil when several sessions changed, while status changes are still reported one by one. Entries are found by ID in a hash table, and the 2510 sessions take about 3 MB.

The service archives a session alone: its subagents stay unarchived, listed while their parent is not, so the registry held subagents whose parent it did not know, and a list such as drover's could not tell the parent archived from deleted or not loaded; it showed them at the top of trees of their own. The registry now holds the sessions above those it holds, at any depth (=opencode-state--parents-wanted=): once the listing ends, the parents it lacks are fetched, archived ones included, with those the previous stream held kept until fetched again rather than dropped and fetched anew, and once loaded, a session fetched has its parent fetched in turn when missing. A parent deleted answers 404 and is let go. Archived parents are entries as any other, which =opencode-state-sessions= leaves out unless asked for archived ones; one whose subagents are gone is let go at the next rebuild. It costs a request per such parent, of which there are few.

A rebuild keeps the previous stream's entries until the listing ends, so lists do not empty while it runs, but treats none as current. When it ends, the entries the service no longer listed are dropped, except those of sessions open in a buffer, which are fetched: a session with a buffer always stays in the registry, archived or older than =opencode-state-recent-limit=, and =opencode-state-sessions= lists it even archived. A buffer opening after the listing fetches its session when the registry lacks it. =opencode-state-recent-limit= is now nil, all, by default; a number still caps the sessions listed, as it once set how many the single page held.

The service does not record when an execution started, nor when it asked a request it lists. A running turn's start is taken as the first message after the transcript's last idle marker, skipping agent, model and location switches, which happen between turns; a request's time comes from its ID, whose first 48 bits are the creation time in the service's ID layout, and a request the registry already knew keeps the time it had.

Unread is the service's, shared by every client: a session is unread when its idle time is newer than its viewed watermark. The registry projects both as the service does: an end of execution sets the idle time to the later of the event's time and one millisecond past the previous idle time, and an interruption by the service shutting down changes neither, since the restarted service resumes the turn. An entry fetched after an event may already reflect it, so a held or queued end of execution is not counted again when the entry's idle time already reaches the event's: counted twice, the idle time would run one millisecond ahead of the service's, which ignores a view of an idle time newer than its own, and the session would stay unread. Posting the view only when unread, and once per watermark while it is in flight, keeps the selection hooks from flooding the service. A caller told of the outcome, as drover marking thousands of sessions seen a few requests at a time, is so of the request in flight for its watermark, joining its callbacks, and at once when the session is not unread: it asked for nothing to be sent.

Prompt-cache expiries, which only my fork reports, are kept apart from the entries, in a table of their own: the service lists them for every session with a live cache entry, the registry's or not, archived sessions included. They are listed whenever the stream connects, alongside the bootstrap; =session.cache.updated= then carries each session's new expiry after every provider response, and events received while a listing is in flight are held and applied over its answer, which may predate them. Nothing reports an entry running out, and once one has, a longer-lived entry of a shorter prefix may still serve the session (a system prompt cached for an hour under a conversation cached for five minutes), or a fork may have refreshed its parent's entry without an event to the parent; so one timer, set a second past the earliest known expiry, forgets the expiries that passed and lists them all again. A listing supersedes the one in flight, and the timer only ever waits for an expiry still ahead, so listings never loop. A service without the route answers an untagged 404: it then has no expiries, and is not asked again until the stream reconnects, maybe to a newer build; any other failure keeps the expiries known until the next one passes. An expiry names the tokens its entry covers and, from newer builds of the fork, =promptTokens=, the whole prompt of the session's last request, kept as =:prompt-tokens= so that lists can tell what share of the conversation a next turn would read from the cache; an older build leaves it nil.

Each entry carries the session's context size, as the session buffer counts it: the token counts, input, output, reasoning and cache reads and writes, of its newest assistant message reporting usage (=opencode-context-size= is that rule, for both). The end of every step reports it, and so does a step failing after the provider answered, whose message keeps that usage; the buffer notes both, so that streaming a turn leaves the size replaying it finds. Neither a session's info nor the session list has it, and no route lists it for several sessions: =session.tokens= sums every step, and the fork's cache listing covers only live cache entries. The cheapest source is the session's newest assistant message, =GET /api/session/:id/message?type=assistant&order=desc&limit=1=, the next one only when that step still runs or failed before the provider answered. Fetching it for every session the bootstrap loads would cost one request per session, thousands, on every reconnection, and each answer holds a whole step with its tool outputs; most of those sessions are never displayed. So the size is fetched only when a client asks for it (=opencode-state-context=), from a timer since clients ask at redisplay, which also lets one redisplay's asks queue up, coalesced per session, a few at a time (=opencode-state-context-requests=), in the order asked. A session the registry saw created starts with none known to be needed, and the end of a step settles a size without a request.

A compaction replaces the conversation, and nothing measures what it left until the next step ends; a manual compaction leaves the session idle, so that may take long. The compaction's own usage is no answer: it is that of its request, which read the conversation it replaced, and it sums every call the compaction made. My fork reports, on =session.compaction.ended= and on the completed compaction message, =context=, the service's estimate of the next request: system prompt, tools, the summary with the messages it keeps verbatim, and what followed, as the service estimates a request no step measured yet. A completed compaction settles the size to that estimate, marked =:context-estimated= in the entry and =opencode-session-tokens-estimated= in the buffer, until a step reports usage; without one, from a native compaction, whose encrypted window cannot be measured, or another service, the size is unknown until then, which is what OpenCode's own clients show after any compaction. Fetched, the size is that of the newer of the newest assistant message reporting usage and the newest completed compaction, the order replaying the transcript follows: compactions are paged from the newest, =type=compaction=, until a completed one or one older than that message. Messages are created as they are appended, so their creation times order them as the transcript does; a manual compaction's message has the ID of its =/compact= request, made before steps that ran while it waited, so IDs do not.

A fetch in flight is superseded by an event settling the size meanwhile, which is at least as recent as its answer, and by a committed revert, which removes messages the answer may still count; the revert also forgets the size, which is fetched again when asked for, as the buffer reloads its transcript then. A reconnection may have missed steps, and the service updates a session whenever a step ends or a revert is committed, but not when a compaction ends. So a size known when the stream dropped is only carried: once a fresh entry, from a page of the listing or a fetch, replaces its session's, the size stays only while the service's update time is not past the old entry's, and with it its estimate mark; a size settled since the rebuild began, by an event or a fetch, stays whatever the page holds, being newer. A session seen to start a compaction and not to end or fail it keeps no size across a rebuild: it is forgotten as the rebuild begins, rather than shown until the session's page arrives, and fetched again when asked for, until a fetch begun since finds no compaction running; the mark goes with the entry when the listing drops it. Fetches queued or in flight are queued again, since their answers belong to the stream that dropped. A failed fetch is not retried on every redisplay, only once the stream reconnects and a client asks again. Sessions the registry does not hold, such as archived ones drover lists from =opencode-fetch-sessions=, have no size: there is no entry to keep current, nor events to follow.

* Displays without a buffer

The session mode line's details are functions of an agent, a model reference, a token count and a directory, in =opencode-display.el=, so that other packages' lists show every session's agent, model, provider, variant and context as the mode line does, from the registry rather than a buffer: the mode line draws its agent with =opencode-agent-display= itself, so that a list's agent has its name, weight and colour. They read the location's cached catalogs and never wait, being called at redisplay: a value needing a catalog not fetched yet is nil, and the fetch is queued, once per catalog however many displays asked, and started from a timer, at most =opencode-catalog-requests= at a time, those not cached before those being renewed; =opencode-catalog-changed-functions= run when it arrives. A selected variant needs no catalog; a default one needs both the model and the provider catalogs, as the request it reproduces merges their settings. The mode line falls back to the agent, model and provider IDs until the catalogs arrive, as it always did.

A reconnection used to forget every catalog, since the service may have restarted with another configuration. With 53 locations in use, that refetched 114 catalogs after every reconnection, waking from sleep included, and each arrival forced every mode line of every frame to be redrawn: with 22 frames and 25 windows a forced redraw costs about 40 ms, so a reconnection held the main thread for seconds. Catalogs almost never change across a reconnection, so they are now stale while revalidated: the stream's opening marks every cached catalog stale, displays keep showing it, and the first display asking for one again queues its fetch, so that only the catalogs in use are fetched, and only on demand. An answer equal to the cached catalog changes nothing: no hook runs, no generation grows, nothing is redrawn. A command fetching a catalog (=opencode-catalog-fetch=, =opencode-catalog-wait=) gets a stale one renewed first, since it acts on the service's current configuration. An event saying a catalog changed (=agent.updated=, =model.updated=, =provider.updated=, =integration.updated=, =command.updated=) marks it stale and fetches it at once, without waiting for a display to ask; a fetch running then may answer from before the change, so another follows it, and an answer to a request begun before the stream reopened stays stale. A fetch that failed is not retried by displays, which ask at every redisplay, until the stream reopens or an event says the catalog changed.

A catalog that changed bumps =opencode-catalog-generation= and its location's count, =opencode-catalog-location-generation=, and updates only the mode lines of that location's session buffers shown in a window, with =force-mode-line-update= in each, from a zero-delay timer, so that any number of arrivals in one tick costs one pass. The mode line's segments are keyed on their location's count rather than the global one, so that a catalog arriving for another location recomputes nothing, and on the count of stream openings, so that a session buffer's mode line asks for its stale catalogs again once after a reconnection, when its resynchronization redraws it.

A session may live in a directory deleted since, such as a scratch worktree, and the service answers its location's requests 404 =LocationNotFoundError=. Displays ask for a missing catalog at every redisplay, and a failed fetch was reported for every catalog of every such location, in the echo area and =*Messages*=, and again after every reconnection, which forgot the failure. Such a failure now marks the location missing (=opencode-location-missing-p=): its catalogs count as cached and empty for displays, which show identifiers, as for a model a catalog lacks, rather than nothing; no display asks for them again; the absence is logged once per location, out of the echo area; and =opencode-catalog-changed-functions= run once, so that lists redraw with the identifiers. A reconnection marks the location to be checked once more, displays showing identifiers meanwhile rather than flickering to nothing, and an event of the location, or any answer from it, brings its catalogs back. A command asking for a catalog hears of the failure, as of any other.

* One look

The session mode line, the pickers and drover's lists showed sessions each their own way: the mode line a check mark for an idle session and a timer for a working one, in faces of its own, the pickers the same icons in other faces, drover a third set of faces, and its own options for the same icons, animations, agent faces, efforts, context and prompt-cache bars, and number formats.  A change to one look was a change to three, and they drifted: drover's waiting icon was gold, opencode.el's orange.  =opencode-look.el= now holds every one of them, and drover requires it and uses it for the sessions of every backend; its former options and faces are obsolete aliases of these, so that customizations of either keep working.

Where definitions differed, one was kept: drover's icons, animations, number formats and context wording, which the list the user reads most showed; opencode.el's faces where its colour roles mattered, the waiting status inheriting =opencode-attention=, as anything waiting on the user does, rather than =warning=, which themes may give the colour of other roles, and a retrying status in the working face, italic.  An entry of =opencode-session-status-icons= in its former form, (STATUS ICON FACE), still gives its icon: the faces are the statuses' own now.  The pickers title a session in the face of where it is in Emacs, as drover's lists do (=opencode-session-place=), and show the archive's icon; they leave idle titles undimmed, which in a minibuffer of mostly idle sessions would dim most candidates.

* An animated status

A working or retrying session's icon turns through the frames of =opencode-session-status-animations=, every =opencode-session-status-animation-interval= seconds, in the mode line as in drover's lists.  The frame shown comes from the clock (=opencode-session-status-frame-index=), so that every animated icon shows the same frame at the same time, and timers tick in the middle of a frame (=opencode-session-status-frame-delay=), so that one running a little late or early neither shows a frame twice nor skips one.

Emacs has no way from Lisp to redraw one window's mode line alone: =force-mode-line-update= redraws those of the windows showing the current buffer, and with ALL every mode line of every frame, which costs about 30 ms with 22 frames.  So one timer, for every session buffer, forces the mode lines of the buffers drawn animated last, and only those a window of a visible frame shows; a mode line drawn animated asks for the timer, which drops a buffer no longer shown or no longer animated, and stops when none is left, or when the pace changed, the mode lines then drawn starting it anew.  Nothing ticks while no animated icon shows.  Every frame is padded to the room of the widest frame or still icon, measured in the mode line's face but without its box: the box draws its edges around the whole mode line only, and measured alone, an icon counted them when a font drew it but not when no font had it, Emacs then drawing a box of its code, so that with a font lacking the icons the still icon took 2 pixels less than the frames.  The mode line is fitted with the still string: a frame changing fits nothing again, and only the tab, already made at every call, takes the new frame.

What the registry tells changes the icon without the buffer changing: a turn ended unseen, a subagent at work, the archive.  The registry keeps each session's subagents (=opencode-state--children=), as entries are stored, so that what a session's subagents do costs its subagents rather than every entry, and counts its changes (=opencode-state--revision=), until which the part of the mode line taken from it is kept.  A change of the registry compares, after the tick, that part for each session buffer shown, and updates only the mode lines it changed.

=dev/bench/run.sh= with =BENCH_RECONNECTS=0= measures it in the scene of [[*Mode lines at redisplay][Mode lines at redisplay]]: 22 frames, 25 windows, 26 session buffers with long transcripts, moody and minions.  With one animated window, a tick costs 8 µs of Lisp, the mode line it redraws 38 µs, and the redisplay it causes 3.0 ms, against 0.26 ms for a redisplay changing nothing; with the 24 session windows of 21 frames all animated, a tick costs 0.16 ms of Lisp, 24 mode lines 0.97 ms, 40 µs each, and the redisplay 29 ms, what forcing every mode line costs.  Left alone for 3 s, the timer ticked 20 times, 6.7 a second, the main thread never held more than 16 ms with one animated window, 41 ms with 24.  Most of a tick is Emacs redisplaying the windows of the buffers forced, which a buffer's mode line forced re-lays out without its usual shortcuts; it grows with the windows animated, not with the frames.

* Mode lines at redisplay

A session's mode line is computed again whenever its window's is redrawn: on every streamed chunk, whenever a window changes, and for every window whenever anything asks for all mode lines. Its Lisp cost was about 0.3 ms, mostly measuring and fitting the details. It is now cached at three levels: the segments, keyed on what they show as above; the details at every level with their pixel widths, keyed on the segments and the mode-line font; and, per window, the fitted title and details, keyed on the status icon, the segments, the buffer name, the window's width, the font, the mode-line height, whether moody is in use, and the rest of the mode line. The rest can change at any time, through minor modes, =global-mode-string= or another package, and only its text with its properties tells, so it is formatted at every call and compared with what the cached fit saw; that formatting is most of what remains, about 0.1 ms with moody and minions. The status is made again only when the pending requests, the status, the retry, the registry's part (see [[*An animated status][An animated status]]) or the look's options change, and the adapted format only when the default format or =mode-line-modes= change, compared by value since packages change them in place. The moody tab is drawn at every call, as moody draws the selected window's differently.

Emacs's default process filter has every mode line of every frame redrawn after each chunk of output it inserts, which made each request answered cost a forced redraw of all of them, hundreds over a reconnection. Requests never show their buffer, so connections read their output with a filter of their own, which redraws nothing.

=dev/bench/run.sh= measures this in a graphical =emacs -Q= dressed as a heavy user's: FiraCode Nerd Font, the tron-legacy theme, moody and minions, 22 frames and 25 windows showing session buffers of distinct locations, and a list drawing all 120 sessions of 53 locations with the displays, redrawn 0.1 s after the registry or a catalog changed, as drover does. The fake service runs in a batch Emacs of its own with the recorded catalogs, the model catalog five times its size. It reports, for the first load and for each reconnection, the time from =server.connected= until nothing was in flight for two seconds, the longest gap between ticks of a 10 ms timer, the time spent in gaps over 50 ms, the forced and targeted mode-line updates, the catalog requests and announcements, and the calls of =opencode-mode-line= with their cost; then the cost of a redisplay, unforced and with every mode line forced. The Lisp time of a session mode line whose inputs did not change fell from 285 to 320 µs to 76 to 138 µs, most of what remains formatting the rest of the mode line. The list is not redrawn at a reconnection, since the registry finds nothing changed, so only the session buffers' catalogs are renewed; a list redrawn then, as drover's is after its own reconnection requests, renews those it shows too, four at a time, redrawing nothing when they are unchanged. The benchmark has since grown into the one of [[*Catching up after a reconnection][Catching up after a reconnection]], whose sessions change while the stream is down.

* No session list

opencode.el has no session list buffer. drover lists the sessions of every agent front end, this one's included, and one listing is maintained rather than two that drift apart: drover reads the registry, which holds every unarchived session, can fetch others, such as archived ones, with =opencode-fetch-sessions=, names projects with =opencode-fetch-projects=, =opencode-project-for-directory= and =opencode-project-name=, shows branches from =opencode-git-branch=, and finds sessions by what was said in them with =opencode-search=. What opencode.el keeps is completion: =opencode= and the other pickers offer sessions in the minibuffer, and commands that act on a session pick one there when called outside a session buffer.

* Full-text search

My fork's =GET /api/experimental/session/search= searches an FTS5 index of user prompts and assistant text; =opencode-search= wraps it for lists such as drover's, which call it only when it is defined and run it as one source among others. So a service without the route must cost them nothing: it answers an untagged 404, as an unknown route does, which =opencode-search= reports as =unsupported= without a message, and remembers by service ID, so later searches fail at once, from a timer, without a request, until a service of another ID, such as a newer build, is reached. A tagged 400 (a malformed cursor or too many terms) is =invalid=, anything else =failed=. Matches come back as plists with their time in float seconds, as elsewhere, and a snippet of one line, at most =opencode-search-snippet-length= characters, the matched words in =opencode-search-match=: the service locates them by character, which Emacs indexes by too. A search is cancelled by the function it returns, which closes its request when one is in flight and in any case keeps both callbacks from running, since a request may be retried on another connection the cancellation does not see. The contract check lists the route as optional, absent from the deployed service's document and checked against the fork's.

* Session pickers

Every picker goes through =opencode-annotated-completion=, with an affixation function. A session's status icon, and the archive's for an archived session, are the candidate's prefix and its project, branch and age the suffix, so neither is matched against the input nor sorted by: the candidate is the title alone, in the face of where the session is (see [[*One look][One look]]). Completion returns a string, so a title given twice gets =<2>=, =<3>= and so on, in display order, and every session stays reachable. The project and branch columns are padded to their widest value among the candidates, and a column no candidate has a value for is left out.

A picker receives session infos, fetched or kept in buffers and notifications, but shows what the registry knows when it holds the session: a buffer's info is not refreshed on every rename, move or turn, and only the registry knows that a turn runs. Projects name sessions only, so pickers name them from the projects last fetched rather than ask the service each time, and fetch them only when none were; a failure leaves the names out rather than the picker. Branches are read from HEAD, as =opencode-git-branch= does for drover.

Outside a session buffer, renaming, archiving, deleting and interrupting pick among the current project's sessions, those =opencode= offers: drover's lists act on any other. Interrupting offers only the sessions =/api/session/active= reports running, which holds whether or not the registry was bootstrapped.

* Live rendering equals replay

Opening a session renders its projected messages; afterwards the event stream drives the buffer. Both paths must produce the same text, which the tests check for every recorded scenario. That rule settled several choices:

- Text and reasoning fragments are keyed by assistant message and per-type ordinal (=MSG/t/N=, =MSG/r/N=), tool calls by call ID, so a late event finds its block wherever the stream left the cursor.
- Reasoning blocks are created on their first text, since encrypted reasoning arrives empty.
- A prompt sent from Emacs carries an ID generated locally, in the service's ID layout, so its echo on the stream is recognized and not rendered twice; prompts of other clients render when the inbox delivers them, where replay places them.
- A prompt typed at an idle session with nothing pending shows where it was typed, and its input gets its message ID, which revert and fork at point need, when the service delivers it: only then does the message exist. Markers keep the input while it waits; a failed or cancelled prompt never gets the ID, and one whose input a reload erased renders on delivery like another client's.
- A prompt typed while a turn runs, or while other prompts wait, leaves the transcript Comint wrote it into and shows as pending until delivered, then renders where the delivery places it, like another client's (see [[*Pending prompts][Pending prompts]]). Should another client's prompt be delivered before one typed at an idle session, that one sits before output that follows it in the conversation: where the transcript ended at its delivery is recorded, and cuts order messages by it, so they follow the conversation, as replay renders it, rather than the buffer.
- A slash command's prompt gets an ID from the service, which only the stream reports, and text expanded from the command's template. The command carries a correlation key in its metadata, which the service passes on to that prompt, so its input gets the prompt's ID; the expanded prompt renders on delivery. A command run by a subagent prompts no message here, so the key is given up a minute after the command's request returned. A shell command makes no prompt: its shell message and result, like other messages between prompts, never start a cut.
- The package tracks its own prompt start marker: =comint-last-prompt= would count the last line of output as the prompt.
- Notices are inserted before the idle prompt, and a turn started elsewhere lifts the prompt first.
- A group of an earlier turn's blocks is made where the next prompt is rendered or sent, from what the buffer holds, never from the stream's order (see [[*Groups of earlier turns][Groups of earlier turns]]).
- A background job's completion is a synthetic message, keyed by its message ID, which its inbox item shares. Its metadata makes it a block of the job's tool, and the element wrapping its text is removed only when it is exactly what the service writes, so an unexpected text shows whole.

* Pending prompts

The service admits a prompt to its session's inbox (=POST /api/session/:id/prompt=, with =delivery= =steer= or =queue=, answers the admitted item) and delivers it later: a steering prompt at the running turn's next step boundary, a queued one once the turn ends, and either at once to an idle session. Only the delivery makes it a message. =session.inbox.enqueued= carries the item, with its text and attachments, =session.inbox.delivered=, =session.inbox.cancelled= and =session.inbox.delivery.changed= name it; =GET /api/session/:id/inbox= lists the items not yet delivered, in delivery order, prompts and others (notes, compactions, moves). =DELETE /api/session/:id/inbox/:inboxID= cancels one, and =PATCH= changes only its delivery: the service cannot change a pending prompt's text. A prompt sent while a turn ran used to show where it was typed, before output that precedes it in the conversation; drover's, sent past the input, showed only once delivered, which looked as if it had not been sent.

Each session buffer keeps its inbox (=opencode--inbox=), in delivery order: what the events and the listing tell, and, for a prompt sent from here, its text as typed, its attachments' labels carrying them. Loading and catching up fetch the listing before the messages, while the buffer withholds its events, so that a prompt delivered in between is in the messages, and one delivered after is in the listing, its withheld delivery rendering it; the listing rebuilds the inbox, keeping what the buffer knew of the prompts still listed and the prompts whose request has not returned. The area showing them is frozen while events are withheld, since a transcript being written may already hold prompts whose deliveries are still withheld, and shown anew once they are applied: a prompt is never both pending and in the transcript. The delivery handler takes a prompt out of the area and renders it in one change, so nothing flickers.

The area lists the prompts not delivered that the transcript does not show: other clients', commands', those sent here while a turn ran or others waited, and those typed at an idle session whose input a reload erased. A prompt sent while a turn runs or others wait (=opencode--defer-prompt-p=) shows at once, before the service even answers. Comint has written it as sent input by then, which is taken out of the transcript again, as if never written, the undo list and the last block kind included; one typed at an idle session with nothing pending shows where it was typed, as the service delivers it at once. A drover prompt sent with SHOW shows at once under the same rule, and otherwise once admitted.

The area is the =before-string= of an empty overlay, not text. The transcript ends at the process mark, where streamed output arrives, and the input starts there; text between them would need every writer, Comint's sending, the input's markers and fields to make room for it, and would become input or output wherever one of them missed it. The overlay sits where the points following output start, at the idle prompt, else at the process mark, and is moved there after every change and before redisplay, which output inserted at the mark and the idle prompt coming and going call for; that costs a comparison when it is in place, and nothing without pending prompts, when there is no overlay. A blank line separates it from what ends the transcript, a partial line of streamed text included. Point can never be in it, so it takes no keys but clicks: its string's keymap withdraws the prompt clicked, and =opencode-edit-pending-prompt=, unbound as other commands are (see [[*Keys][Keys]]), reads the one to withdraw.

Withdrawing asks the service to cancel the prompt, once it took it: cancelling a prompt not admitted yet would do nothing, so a withdrawal waits for the admission, the answer or the event, whichever comes first. The service answers 204 whether it cancelled the prompt or found it delivered already, and the cancellation's event may come after the answer, so unless an event told first, the message is looked up: it exists once delivered, never once cancelled. Cancelled, the prompt goes to =opencode-withdrawn-prompt-function=, the input by default, as an earlier prompt does, every attachment with it, inline data included, from the text kept as typed, else rebuilt from the item: a mention labels itself where the prompt names it, its offsets counted in UTF-16 as the service counts them, other attachments after the text. Skills come back as attachments too, so session buffers now send them. Delivered first, the prompt stays sent and the echo area says so; a service without the route, an untagged 404, keeps it pending and says it cannot withdraw it. A prompt typed here that the service refuses, or another client cancels, shown nowhere else, goes back to the input too. The inbox lives in the session's buffer: the registry follows no inbox, and would have to list the inbox of every session it holds to know their pending prompts, so =opencode-pending-prompts= counts a session's from its buffer, and a session without one has none to withdraw from Emacs; every prompt Emacs sends goes through a buffer, drover's included, opened unshown if need be.

* Catching up after a reconnection

The service replays nothing to a stream that reconnects, so every open buffer must find what it missed. It used to compare its session's update time with the one it fetched when it opened, and render its whole transcript again when they differed or a turn ran. Events never refreshed that time, so every buffer whose session had run a turn since it opened rendered its whole transcript again at every reconnection. With 26 buffers open, some with thousands of parts, a reconnection held Emacs for 9.6 s in one stretch.

The live events tell which messages a buffer renders: the service names a message after the event appending it (=msg_= and the event ID's suffix), a prompt or note after its inbox item, a step after its =assistantMessageID=. So the buffer records the ID of each message it renders, from events and transcripts alike, and whether it is open, as a running step, shell command or compaction is, or finished. Whenever none is open, everything up to the newest message is rendered for good: that message and the end of the transcript, before the idle prompt, are where the buffer is in sync (=opencode--synced=, =opencode-synced-end=), with the state writing more needs, the kind of the last block, the errors shown in the turn and the start of the last answer. Expanding the block ending there writes at that point, which then moves after the expansion.

At a reconnection, every buffer fetches its session, adopting its location, title and selections, then the newest page of its messages, five of them, and pages of 25, 100 and 200 further back until one holds the message it is in sync with. Most buffers missed nothing, or a turn: the first page tells, and a buffer with nothing newer and nothing open writes nothing at all. Otherwise it deletes what follows its sync point, the step that was running included, and writes the messages after its sync message from the state saved there. As live rendering equals replay, that is what a buffer opened afresh shows. When the first page lacks that message, the service is asked whether it still has it: a revert or a fork-and-replace removed it, and the buffer renders its whole transcript again rather than page back through all of it. The status comes from the running sessions, asked once for every buffer.

Answers and events race: an event arriving while a buffer fetches may be in the answer already, or not. So a buffer withholds its session's events from the stream's reopening, and from the start of any whole load, until it has written what it fetched, then applies them in order, and nothing already rendered is rendered twice. An event appending a known message renders nothing; events of the parts of a finished step change nothing, and nor does its start, which the service projects as its message's creation time, so that only a step started again, as after a retry, which starts later, opens its message again; a step still running in the answer has its finished parts noted as shown, and those still empty, whose deltas were missed, are shown whole when they end; a tool call never goes back from finished to running. A withheld end of a tool call shown finished already still runs the hooks of a finished call, as the call did end live, and the status is first set to the one before the first withheld turn event, so that applying them leaves the status they lead to.

Buffers shown in a window catch up first, =opencode-resync-requests= at a time. A reconnection during a catch-up abandons it and begins again; a buffer loading its whole transcript catches up once loaded, as its answer may predate the reconnection. Transcripts are written =opencode-replay-slice= seconds at a time from timers. While a buffer writes its whole transcript, its windows show its start between slices, which redisplay fontified already, rather than the newest text of every slice, tens of milliseconds a slice for a window of Markdown; they go back to its end once it is written. Summaries written meanwhile are fitted only where a window shows them, or will once redisplayed: fitting thousands after each slice cost tens of milliseconds, and those elsewhere are fitted when scrolled to.

=dev/bench/run.sh= now opens 26 session buffers in its graphical =emacs -Q= with the user's garbage collection thresholds (100 MiB, 0.5), 24 of them shown in 21 frames, three of them split, the list in the 22nd: four transcripts of 400 turns, eight of 60 and fourteen of 8, of six parts each (a prompt, reasoning, a file read, a shell command with its output, an answer in Markdown, with a table every seventh turn, and the turn's end), 2400 parts for the long ones. While the stream is down before each reconnection, the service adds a turn to half of the open sessions, the long ones included, and starts or ends a turn in another, which then runs at the reconnection; before the second, it also reverts a long session's last turn and replaces it, so that one buffer must render its whole transcript again. Three sessions of the list live in directories that do not exist. After the last reconnection, every open buffer is compared with its whole transcript rendered afresh. * Writing a transcript in linear time

Writing a transcript whole cost time quadratic in its length, which made a reconnection rendering a few long ones take seconds. Three causes stacked, which =opencode-test-replay-time-linear= now guards against: a transcript four times longer must take less than eight times as long.

The undo list keeps only the prompt's edits: an output change drops its records and shifts the prompt's by its length. Replaying a prompt runs Comint's input sending, whose records, made at the input, are not output; they were kept, two per prompt, and every later output change shifted all of them, which was the 1250 profiler samples of =opencode--undo-shift= at the user's reconnection. They also let undo rewrite the transcript. A transcript is now written under =opencode-without-undo=, which records nothing and shifts the prompt's records once afterwards, by how far the input moved; so is another client's prompt rendered live.

=comint-output-filter= makes three markers on every call, which stay in the buffer until a garbage collection, and every insertion adjusts every marker of the buffer. With the user's large =gc-cons-threshold=, tens of thousands accumulated while a transcript was written. Session buffers write with =opencode--output-filter= instead, which does exactly what Comint's does with markers it reuses, the prompt's included, and so does the idle prompt.

Rendering each table had set up =markdown-ts-mode= in a fresh buffer, which looks up every grammar: 8 ms a table, now 0.5 ms with one buffer set up once. Scanning a text block for its tables parses the transcript; a block without a pipe has none, and is no longer scanned. And a tool call's path is made relative to the project through true names, which stat every directory of both; the result is now cached. Byte-compiled, writing 1000 turns of four messages took 6.7 s, and four times as long for twice as many; it takes 0.1 s, and 4000 turns 0.37 s.

* Points that follow output

A point at the end of the transcript or in the input follows output, in the buffer and in every window showing it, selected or not; one elsewhere in the transcript keeps its text, and its window its start. The end of the transcript starts at the idle prompt when one is shown, whose markup is hidden, so that a point before it looks the same as one after it; otherwise at the process mark.

Comint provides this for the output it writes: the buffer's point is saved with a marker that advances, window points advance through =window-point-insertion-type=, and =comint-postoutput-scroll-to-bottom= moves window points left at the process mark after the output and scrolls their window to it. Output written otherwise needs the same care, which =opencode-keeping-followers= gives it: it records each following point by its distance from the end of the buffer, which writing, replacing or deleting transcript text leaves unchanged, and puts it back there afterwards. It wraps the expansions written at the process mark, tables aligned in place, which may also grow past the process mark (the process mark then moves after them, or their tail would become input), and table reflows. Nested calls leave the points to the outermost one, which saw them before anything changed: rewriting a block ending the output deletes it first, which brings the points that were in it to the process mark.

=opencode-call-preserving-viewport= wraps output that must not move what the user reads: the prompt shown when a turn ends, notices, other clients' prompts, permission fallbacks, question blocks, rewritten expansions. It keeps the following points so, which also keeps a point's place in an input that rendering another client's prompt lifts and puts back, and the others with markers that stay before what is written at them. Following windows are left to Comint and redisplay, as for streamed output.

Markers do not survive reloading, which erases the buffer: =opencode-save-viewport= records the following points by distance, the others by line and column, and their windows' starts by line, and =opencode-session-reload= puts them back once the transcript and the input are written again. A desktop entry marks a point that followed output, which then comes back at the end of a transcript that may have grown. A window takes the insertion type of its point from the buffer it is shown, so the windows showing a restored placeholder are shown the session buffer again once its mode is set, which also gives them its margins.

Batch Emacs has windows but never redisplays them, so the tests check window points and starts in real windows, through the event handlers, rather than what is visible.

* Fontification that survives

Markdown is fontified by =markdown-ts-mode= as text streams in. Regions that must keep their own faces (verbatim output, tool summaries, buttons) are marked with properties the Markdown fontifier skips, and buttons are made after fontification from registered buttonizers. Font-lock also owns =display=, removing it at every fontification, so a renderer laying text out with it, as a table renderer pads a cell holding an emoji wider than two columns with a space a few pixels wide, records it with =opencode-keep-display= and every fontification puts it back. Half-typed Markdown never turns the transcript red: the parser's error feature is off.

Links are buttons made from output, never by font-lock, so that they are only ever in the transcript: =RET= on one follows it, while =RET= in the input sends it. A prompt, once sent, is part of the transcript too, though Comint writes it as input rather than as output: its links are made when it becomes sent text, in =opencode-highlight-input=, which marks every prompt sent from the input, written for another client or replayed, the reload and the catch-up included. Without them, =M-n= and =M-p= skipped a URL written out in a prompt, and =RET= on it, finding no button, took the prompt as old input and sent it again; =RET= on an earlier prompt now never sends it (see [[*RET in the transcript][RET in the transcript]]). Prompts rendered before that kept none, nor did reloading the package give them any: a session buffer open across the upgrade kept its prompts without links until reverted, and one whose only link was in a prompt had no button for =M-n= to find. So loading =opencode-links= links the sent prompts of every session buffer open, before the process mark, with the same buttonizers, which skip the links already made, as a change of properties only, recorded neither in undo nor as a modification. markdown-ts also links URLs written out, at redisplay, in the input too, and opens them as mail; session buffers drop that, and the buttons it makes of the Markdown links typed in the input. A URL written out has no closing delimiter, so it becomes a button once a character that cannot continue it follows, or once the block writing it ends: a streamed URL is never a button of half its length. A link of another kind holding it, such as an Org link whose description arrives later, takes its place. URLs are links in code spans and blocks too, the link face added over the code's; in summaries they are not, as a summary is cut to fit and its keys toggle its block. Verbatim text loses the buttons Markdown makes in it at every fontification, so a durable button keeps its category, which gives it its keys, with its other properties, and the link face is a kind added to =verbatim= rather than one replacing it.

* Parsers that go with their text

markdown-ts parses each inline region, a paragraph, a list item or a heading's text, with a tree-sitter parser of its own: treesit.el keeps it in an overlay over the region (=treesit-parser=, =treesit-parser-local-p=), finds it again there when fontification updates the region's ranges, and deletes it only when such an update finds the overlay stale. Every change of the buffer's text edits every parser the buffer holds, and redisplay updates the ranges of every changed region, so a parser costs as long as it lives. Session buffers deleted the overlays holding parsers without deleting the parsers: reloading erased the buffer with =remove-overlays=, catching up deleted the overlays of the running step it wrote again, and lifting the prompt split, with =remove-overlays=, the overlay of an answer that had grown over the prompt and the input typed after it, leaving two overlays holding one parser, which two regions then shared. Each lost parser lived as long as the buffer, and its region was given another at its next fontification. A user's session buffer held 3221 parsers, 2793 of them without an overlay, and more every few minutes; creating parsers took 5.5% of the main thread, and querying their ranges allocated 53 MB in 250 s.

So the parsers go with their text. =opencode-delete-overlays=, which reloading, catching up and lifting the prompt use instead, deletes only the overlays lying within its region, never splitting one, and the parsers they hold. Text deleted any other way, a block collapsed or rewritten, a summary replaced, a table aligned, a fallback line or the input deleted, has its parsers deleted by change hooks: the parsers whose overlays lie within the text a change replaces are noted before it and deleted after it, when it changed the text rather than only its properties, which leave =buffer-chars-modified-tick= alone. A buffer that turns its change hooks off, as deleting an attachment's label does, calls =opencode-delete-parsers= itself. Killing a buffer frees its parsers with it.

Buffers set up by earlier versions keep their orphans until pruned: a parser no overlay holds, or only an empty one, is deleted, and so is an overlay holding a parser deleted already or one another overlay holds too. Each deletion walks the buffer's whole parser list, so a buffer prunes them by itself a slice of 30 ms at a time, from timers: the first time this version fontifies it, and whenever it reloads or catches up. =opencode-session-prune-parsers= prunes at once.

| Opening                             |   3002 |  3002 |
| One reload                          |   6003 |  3002 |
| Three reloads                       |  12005 |  3002 |

| Per edit, after three reloads | Before   | Fixed    |
|-------------------------------+----------+----------|
| Inserting                     | 5.6 ms   | 0.085 ms |

A buffer like the user's, 2520 orphans of 2940 parsers, prunes in 23 ms.

* Requests that wait

Permission requests and questions mark the block of the tool call that raised them and never take focus. A request whose block has not been inserted yet prints a fallback line that the block replaces. Requests of a subagent mark its block in the parent session. Answers from any client resolve them through =permission.replied= and =form.replied= or =form.cancelled=.

A request is answered in a transient, which remembers the request it shows (=opencode--active-form=, =opencode--active-permission=) so that an answer from elsewhere closes it, and which leaves a request pending when quit or suspended, from =transient-exit-hook=. That hook runs on the exit of any transient, and a transient opened by a suffix of another, such as drover's menu, is set up before that other one finishes exiting: its exit then comes once the request's transient shows, and counted as the request's own, it forgot the question it showed, whose next answer failed. So the exit counts only once the request's transient is no longer shown. A question can also be answered elsewhere while a suffix runs, such as while a custom answer is typed after the transient was left; the suffix then lets it go.

A list such as drover's answers in place: =opencode-respond-session= with IN-PLACE opens the transient from the selected window, without showing the session's buffer, which would take the user away from the list. The request's state stays in that buffer, opened or refreshed in the background when needed, so that the answer is posted and recorded exactly as when given there; the transient's state records that it is answered in place, since a question re-shows its transient from a timer for every question, after any dynamic binding ended. The context the transcript gives otherwise goes into the transient: a heading naming the session, and for a file permission the change asked for, which its block shows in the transcript. So the menu must show, whatever =transient-show-menu= says, and the keys scrolling the transcript scroll the menu when no window shows the session.

The service neither answers nor dismisses a request when a prompt arrives: it admits the prompt to the session's inbox, and delivers a steering one at the next step boundary, which a step waiting on its tool calls reaches only once the request is settled. A prompt sent then would wait unread, which looks like a lost =RET=, so a send check asks first. A subagent's request holds up its parent only through a foreground call: the subagent tool then blocks the parent's step on the subagent's job until the subagent's turn ends, while a background call (=background=, or a foreground one the user moved to the background) returns at once and the parent goes on, its next step, or a new turn when it ended, reading the prompt. So the check counts the session's own requests, from its buffer and the registry, and a subagent's only when each session from this one down to it runs the next in the foreground, which shows in its buffer as a subagent block still running (a background call's block is completed, its metadata still running). The registry does not know how a session runs its subagents, so below a subagent without a buffer requests are left out rather than warned of wrongly; the leaf asking always has a buffer, opened when it asked.

Answering does not have that limit: any request of the session's tree can be answered from the session, in place or not, its own first, then the oldest of its subagents' at any depth, foreground or background (=opencode-tree-requests=), from the buffers below it and the registry, which knows subagents without a buffer. A parent once answered only through its blocks of waiting subagents, which only a foreground call marks: a background subagent's request could be answered only from its own buffer, or drover's row of it.

* Keys

The package binds only what a Comint or special-mode user expects, plus =C-c C-o= to open links, as in Org, and the keys of its own transients, blocks, links, pending prompts and the desktop placeholder. Every other command is left unbound, so that one set of maps can cover several agent front ends: drover provides them, acting through functions that need no buffer (=opencode-session-delete=, =opencode-session-fork=, =opencode-session-compact=, =opencode-rename-session=) and commands that work from any key (=opencode-attach=, =opencode-mention-subagent=, =opencode-insert-slash-command=). The commands that edit the input act on the current buffer when it is a session buffer, and otherwise on the last selected one, since drover may run them in a session buffer that is not selected. =/= and =@= keep their electric meaning at the input, sharing the code of those commands; =opencode-insert-slash-command= puts a command at the start of the input from any key, the text already typed becoming its arguments, as typing =/= there does, and replaces a command the input already starts with rather than nest one in another's arguments.

Hints that name a command, in messages, notices and tooltips, go through =opencode-command-keys=, which asks =opencode-command-keys-function= for the keys first, since with few keys of its own =substitute-command-keys= would mostly find none; drover answers with its own. Comint refusals name the keys of what to do instead the same way.

A session buffer inherits =comint-mode-map=, whose keys show through once the package binds nothing over them. Its process is a pipe that runs nothing, so the commands meant for a subprocess are remapped, which keeps their keys and menu entries meaning what they mean in Comint: an OpenCode equivalent where there is one, else =opencode-comint-unsupported=, which refuses with the reason. The rest only move, search, copy or edit text, and stay.

Remapping rather than binding keeps the standard keys' standard meaning and covers the menus too. =revert-buffer= in a session buffer renders its transcript again.

Comint takes the input by deleting it and inserting it again as sent text, which deletes the labels of its attachments, and deleting a label drops its attachment. That deletion used to be spared only while =this-command= was =comint-send-input=, but =RET= runs =opencode-send-input=, and an input sent once its session left the archive is sent from a callback, where =this-command= is whatever command ran last: the labels' attachments were dropped and the prompt went without its files and mentions. Whatever sends the input through Comint now goes through =opencode--comint-send=, which binds =opencode--sending-input= to the buffer while Comint takes it, until =opencode--send-input= receives it; =comint-send-input= is remapped to =opencode-send-input=, so that any key bound to it does too. =M-x comint-send-input= finds no remapping, so =comint-send-input= is advised, as =cd= is: in a session buffer, a call without arguments made outside =opencode--comint-send= runs =opencode-send-input=, with its checks, the archive and the attachments, and a call with arguments lets Comint take the input with the flag bound, keeping a copy that a send check cancelling it puts back; elsewhere, and for the text a session buffer writes through Comint with another sender, such as another client's prompt, the advice only calls Comint. =opencode--comint-send= and a guard bound while =opencode-send-input= runs keep it from recursing. A label deleted by editing still drops its attachment.

Rendering lifts the input too: another client's prompt is written before it, which takes the input out and puts it back, and a transcript rendered again, on a reload or a catch-up that finds its sync point gone, erases it and writes it again. Both kept only the text: the attachments of a lifted input were dropped by the deletion, those of an erased one stayed with no label left to remove them by, and a label became plain text. Every path lifting the input now goes through one pair, =opencode--take-input= (=opencode--copy-input= with TAKE) and =opencode--put-back-input=: the input's text with its properties, its labels as offsets with their attachments and displays, and the next prompt's attachments, which leave =opencode--attachments= while the input is out, so that nothing is sent without its label meanwhile; the labels' overlays are deleted before the text, so that removing it drops nothing, and made again, with the hook removing an attachment, when the text is back. A transcript that cannot be loaded again puts the input back as well, rather than lose it with the failure.

Comint binds no =TAB=; Shell mode binds it to =completion-at-point=, and so does =opencode-tab-dwim= at the input, while the read-only transcript keeps =TAB= for its blocks and buttons. Comint's own completion function reads any word at point as a file name and is exclusive, so a word that names no file would fail before the global completion functions, such as a dabbrev function, are tried: session buffers call it through a wrapper making its file names non-exclusive.

* RET in the transcript

Comint's =RET= on old input copies it to the process mark and sends it at once; in a session, that sent an earlier prompt again, unasked and unedited, as soon as =RET= was pressed while reading it. =RET= in the transcript now sends nothing: =opencode-send-input= hands the active region, else the line at point (=opencode-old-input-at-point=), to =opencode-old-input-function=, called in the session buffer, point and region as the user left them, with that text and the buffer. What is done with it is that function's to decide, so that opencode.el need not know drover: nil puts it in the session's own input (=opencode-put-old-input=), replacing a blank input and following a typed one after a blank line rather than erase a draft, as Comint's =comint-delete-old-input= would; drover's OpenCode backend sets it, when nil, to its prompt key's command, which quotes the line or the region in its prompt buffer as it does in any buffer, the text given being the same. =C-c RET=, Comint's =comint-copy-old-input=, keeps its name's meaning and always puts the whole prompt in the input, and falls back to Comint elsewhere.

=RET= first quoted on earlier prompts only, and elsewhere in the transcript did nothing; the request was for it to quote any line outside the input, which it now does: an earlier prompt's, the agent's text, a block's or a group's summary, a notice. What has keys of its own keeps its =RET=, since the =keymap= of a text property or an overlay comes before the major mode's: links, whose button keymap follows them. A summary's keymap gave =RET= to its block's toggle, which it gives no more, so that =RET= quotes there too; =TAB= and a click on the box toggle, as before. The text is the line or the region as it shows (=opencode-transcript-text=): what overlays hide is left out, the blocks of a collapsed group and the prompt string before each prompt, so that a summary quotes its icon, name and description, and a region over a collapsed group quotes the group's line, not the blocks it hides; the arrow before a summary is an overlay's string, never buffer text. What markup hides stays, as text properties hide it rather than overlays: the Markdown is quoted as written, its link targets included, which a reader of the quote needs more than the transcript's look. Trailing whitespace goes, and a blank line quotes nothing, which the echo area says rather than hand an empty quote over.

=RET= first handed the whole prompt over, and drover put it in its prompt with the prompt's session chosen as where it went, to be edited and sent again; the request had been for =RET= to do there what drover's prompt key does, quoting the line or the region, which it now does. The mouse was left with Comint's look for earlier inputs: Comint gives sent input =mouse-face= =highlight= and a =help-echo=, which the package overwrote with its own hint, "RET, mouse-2: edit this prompt to send it again", and =mouse-2=, Comint's =comint-insert-input=, did what =RET= did. A prompt now takes nothing from the mouse: =opencode-highlight-input= removes Comint's highlight and help as it marks a prompt sent or replayed, and =comint-insert-input= is remapped to =opencode-run-global-click=, which runs the click's global binding, as Comint does where there is no input. Loaded over an earlier version, the package takes them from the prompts of the session buffers open, their links keeping their own.

The prompt is found by the =opencode-prompt= property every sent or replayed prompt carries, rather than by Comint's input field: it is the run of that property at point, or ending at point, so that =RET= at the end of its last line counts, and the line is taken within it, without the hidden prompt string before its first line. A link in it is a button whose own keymap takes =RET= and the click first, so links keep following.

Attachments leave only their labels' text in the transcript. Those that can go again keep their attachment as the label's =opencode-sent-attachment= text property: subagent mentions, and files read from a file URI, which come back as attachments when the file is still there. A prompt rendered from the service gets them from its message's =files=, whose =source= tells the URI a file was read from, and =agents=; a prompt sent from the input, from the labels Comint's sending took along (=opencode--input-sent=), before their overlays go. A file sent inline, a buffer, a region or a pasted image, keeps no property: its data would stay in the buffer for as long as the transcript. =opencode-old-input= returns the prompt with those properties, and =opencode-put-old-input= makes each such label an attachment's label again, deleting it dropping the attachment, as for a typed one; a function writing elsewhere uses the text.

* A read-only transcript

Text typed with point in the transcript went in it, Comint's output being as writable as its input, so that a key pressed while reading changed the context shown, in a way no one could tell from the server's. The transcript, everything before the process mark, is read-only to the user now; point goes anywhere, and the input after the mark stays as editable as ever.

Read-only is a text property, as Comint's =comint-prompt-read-only= makes it for prompts, rather than a hook refusing changes: a =before-change-functions= function that signals has its hook reset to nil by Emacs, and an overlay would have to follow the process mark through every writer. The property is not =read-only= itself but =opencode-transcript=, which session buffers read as =read-only= through =char-property-alias-alist=. Text copied with its properties goes elsewhere: into a work buffer that measures it, where =string-pixel-width= adds properties to it and failed on read-only text (summaries measured to fit did), into another buffer by =insert-buffer-substring= or a package, where it stayed read-only; the alias makes it read-only in session buffers alone. Yanking drops it (=yank-excluded-properties=, locally), so text copied from the transcript yanks into the input editable, and a summary measured drops it first, as its work buffer takes the session's aliases.

Insertion is refused within text whose =read-only= is front-sticky, or after text where it is rear-sticky. Comint's output carries lists of both, a front-sticky list without =read-only=, so =opencode-protect= adds it there, front-sticky so that nothing goes within the transcript or before it, rear-nonsticky so that the input is typed right after it, with =opencode-transcript= itself rear-nonsticky, and nonsticky by default (=text-property-default-nonsticky=), so that typed text inherits none of it. Output written at the mark is protected as it is written, by =opencode--output-filter=, last, once Comint's prompt properties are set, and by =opencode-insert-output-at=; a sent prompt as =opencode-highlight-input= marks it, with the newline after it. Text written within the transcript is protected by an =after-change-functions= function: a change before the process mark comes from a writer binding =inhibit-read-only=, since nothing else could make it, while one at the mark may be input put back, never protected there. A change of properties alone keeps its text's protection and is skipped, which kept the cost of rendering a long transcript within a sixth of what it was. Comint's output marks text inserted in front of it as output through its =insert-in-front-hooks=, which run after the change hooks and reset the stickiness: protected text adds a function of its own after Comint's. A writer appending at the mark, then moving it, as a table rendered at the end of the output does, moves it with =opencode-move-pmark=, which protects what it passes over; the table functions a user sets are called with =inhibit-read-only= bound. Every write path is tested: each test of the fake service ends checking that every session buffer's transcript is read-only, front-sticky and rear-nonsticky, and that no writer met read-only text, whose error demoted shows in =*Messages*=; another tries an insertion and a deletion at every property change of a transcript after streaming, tables, blocks, groups, the pending area, a reload and a catch-up.

Typing in read-only text signals at every key, which floods the echo area and rings while a key is held. The commands of =opencode-transcript-quiet-commands=, those inserting or deleting at point, typing and yanking and deleting (=self-insert-command=, =/= and =@=, =newline=, =yank=, =delete-char=, =delete-backward-char= and their kin), do nothing in the transcript: a =pre-command-hook= function replaces the command by =ignore= when it would change text before the mark, at point, before it for a backward deletion, at the region's start when it would replace or delete the region, so that =delete-selection-mode= does nothing either. Other edits, transposing or changing case, are refused as by any read-only text, once per key. Killing copies, as =kill-read-only-ok=, set locally, makes it, with Emacs's message saying so: =C-w= copies a region of the transcript rather than refuse it. Nothing tells the user once that the transcript is read-only: typing there does nothing, as asked.

Loaded over an earlier version, the package sets this up in the session buffers open and protects their transcripts, a slice of 64 kB at a time, the first at once and the others from timers, as a transcript of megabytes takes a few hundred milliseconds whole; what is written meanwhile is protected as it is written (=opencode-read-only-upgrade=).

* Boxes under the mouse

A summary line used to take the mouse whole: its overlay's =mouse-face= highlighted it, and a click anywhere on it toggled the block, so that reading or selecting a summary flashed a link. Only its box, the icon and the boxed name starting the line, takes the mouse now: the box's text carries the =mouse-face=, and the summary's keymap binds =mouse-1= to =opencode-mouse-toggle-block=, which toggles the block when the click is on the box (=opencode-box=), the arrow before it included, as the click lands on its first character, and otherwise runs the click's global binding. =TAB= keeps acting on the whole line, while =RET= quotes it (see [[*RET in the transcript][RET in the transcript]]).

Emacs draws text under the mouse in the default face merged with the =mouse-face= alone, never over the text's own face (=face_at_buffer_position= with =mouse=), so the =highlight= of the theme dropped the label's box and italic slant: the glyphs drawn under the mouse were narrower than those laid out, and the name moved. The box's =mouse-face= is therefore the icon's own face, its box and slant included: the icon looks the same under the mouse, and the label, which differs from it only in colors, fills with the block's color, every glyph keeping its width. Both carry one object as their =mouse-face=, since the extent of a highlight is the run of an =eq= value, so the box highlights as one. The icon has the label's box too, which in its own color shows nothing over its filled cell; a box run starts where the face before has no box, so icon and label make one box rather than two, and the label lost its left line, which the icon's gained. A GUI test lays a summary out drawn plainly, and as the display draws it under the mouse, and checks that every glyph is at the same pixel, with the user's font and theme when given; the look before, a =highlight= over the line, moves them.

* Groups of earlier turns

Earlier turns mostly matter by their answers: their blocks, often dozens of tool calls, took most of the screen. So once a later prompt is written, each run of two blocks or more of the turn before it, following one another, collapses into one group. A group is a summary as a block's is, buffer text written before the run by =opencode-insert-output-at=, with an overlay that toggles and fits as any summary's (=opencode--collapsible-overlay=), its data holding its blocks; the blocks stay as they were, hidden by a second overlay whose =invisible= is =opencode-group=, from the end of the group's line to the end of its last block's line, as Org hides an entry, so that the line's newline is the last block's. Its summary counts the blocks in its box and by kind after it, the failed ones in the error face. Expanding a group shows its blocks; a block expanded or collapsed in it moves the end of the hidden text with it. A hidden block gets no keys: =TAB= moving between blocks skips it, and Isearch, finding a match there, expands the group (=isearch-open-invisible=).

Groups are made where a prompt is written: rendered from the service, live or replayed (=opencode--render-user-prompt=), and sent from the input, once the send checks let it go (=opencode--send-input=); a shell command makes no prompt and groups nothing. The turn grouped runs from the end of the prompt before to the new one, found by the =opencode-prompt= property, so that a buffer rendered again, on a reload or after a catch-up that cut it, groups as it grouped live: rendering equals replay here too, which the tests check against a buffer opened afresh. A block joins a group only once done: a tool call finished and waiting on nobody, reasoning ended, a notice. A block that changes (=opencode-refresh-block=) in an earlier turn, finishing, starting or ceasing to wait on the user, groups its turn again: =opencode-group-runs= keeps the groups whose blocks are still a run as they are, open or not, dissolves the others, and makes the new ones, open if one of their blocks was in an open group; a block of a group that only changed updates the group's summary. A permission or a question coming to a block of a group thus takes it out before its form shows.

Points stay where they were: those the new group hides go to its line, the buffer's point and windows' points, and a window starting among them starts there; the others keep their text, as markers do, and those following output their place. Viewports kept around a change (=opencode-call-preserving-viewport=, =opencode-restore-viewport=) bring their points out of a hidden group the same way (=opencode-shown-position=). A group costs a line of text and two overlays and is made in place, so a long transcript renders in about the time it did, and its earlier turns cost redisplay a line each. Loaded over an earlier version, the package redraws the summaries of the session buffers open with their boxes, takes the line's highlight off their overlays and groups their earlier turns, in place, keeping their points (=opencode-blocks-upgrade=).

* Edits only from live turns

Post-edit hooks run from =session.tool.success= of live turns only. A reloaded transcript or a fork is built from projected messages and never reruns them, so files edited long ago are never reformatted; the hooks also check that no transcript is being written, so that neither opening nor catching up ever processes a file. The diff an edit or patch reports gives the line ranges; a write reports none and counts as the whole file. Processing never asks anything: the service writes files behind Emacs, and a stale buffer would otherwise prompt whether to reread it.

Processing runs from events, in the background, so nothing it does may ask a question, which would take the user's minibuffer from a timer and hold Emacs until answered. Visiting a file runs its mode's hooks and applies its local variables, those of a =.dir-locals.el= included, and Emacs asks before applying risky ones: a session editing this very repository, whose =.dir-locals.el= then held a risky entry, opened that question in the middle of a reconnection. Processing now runs under =opencode-without-asking=: only safe local variables apply, nothing risky is offered, =inhibit-interaction= turns any question a mode hook, a lock or a save would ask into an error, which leaves the file alone with a message, and messages stay out of the echo area.

* The prompt cache

The cache guard's report comes from the service, which dry-runs the request the turn would send and compares it with what the provider confirmed it cached. The check runs from =RET=, before Comint takes the input, so declining leaves the prompt untouched; a caller that switches agent or model before sending passes them to the check, so no question appears from an asynchronous callback. Every prompt and command carries =thinkingLoss: "ask"= in its metadata, so the service refuses a turn that would replay stale thinking instead of letting the provider drop it, and consent sends =thinkingLoss: "accept"= on that one prompt. A service without the route answers an untagged 404, and the guard then stays off for it.

* Sending to an archived session

Input sent to an archived session brings it back from the archive first, wherever it comes from: =RET= and =opencode-queue-input= in its buffer, a slash or shell command typed there, =opencode-session-send= and =opencode-session-command=, which drover's prompts and scheduled deliveries use. The restore sits in front of the requests themselves, in =opencode--after-restore=, so no path can skip it. Whether a session is archived is read locally, from the registry, else from the session info of its buffer, which follows =session.archived= and =session.unarchived= for sessions the registry does not hold yet, such as one drover's archived view opened; a session that is not archived sends at once, as before, without a request more.

=RET= runs the send checks first, since they may ask, and a question cancelled must leave the session archived; only then is the session restored. The input waits at the prompt rather than be taken by Comint: a refused restore then sends nothing and leaves the input as typed, attachments included, and the notice saying why is all that changes. Once restored, the input is sent as if =RET= were pressed again at the prompt, with the delivery and the checks' metadata of the first press; =RET= meanwhile only says that it waits, so the checks do not ask twice.

One restore serves every send made while it runs: the sends wait in a list per session and go in the order they were made once the service answered, each in its buffer, or fail together with its error. The answer of =PATCH /api/session/:id= updates the registry and the buffer before they run, rather than leave them to the event, which may come later: a send made between the answer and the event would otherwise restore the session again. The event then changes nothing.

* Default variants

A model reference without a variant sends neither a variant's settings nor its body: the request carries what the provider and model catalog entries configure, and the provider decides the rest. The service never says which variant that amounts to, yet the mode line names it, so =opencode-model-default-variant= reproduces the request: the provider's settings with the model's merged over them, and the model's body overlay, read at the keys OpenCode's variants set; the OpenAI packages add a medium effort for GPT-5. Claude pairs every variant with adaptive thinking, so an effort counts only under it, and what the request leaves unset takes the API's defaults (=opencode-anthropic-default-efforts=), except behind Copilot, which handles Claude's effort itself; binding thinking blocks, from Claude 5.1 on unless the catalog says otherwise, turns adaptive thinking on. The variant named is the one sending the same effort, and none when no variant does.

* No process per request

Each request used to start a curl process, and the stream one per reconnection. Starting a process stops Emacs until the kernel has executed it, which takes a millisecond or two in a fresh Emacs and took up to seconds in a large, long-running one: =claude agents --json= froze it for 1.0 to 8.5 s, and curl processes for 1.3 and 2.5 s. Measured in that Emacs, 3 GB resident and 10 hours old, starting =/usr/bin/true= through a pipe, as =plz= does, took 1 ms at the median and up to 1.5 s, all of it inside the kernel's =posix_spawn=, while a batch Emacs started the same program in 15 ms at most at the same time; through a pty, which forks, 50 ms every time against 2 to 7 ms. The endpoint security agents were not what held it: a binary never seen before took 250 ms to 1.3 s to print, in either Emacs, but only after =posix_spawn= had returned. The spawn's exec closes every close-on-exec descriptor the new process got a copy of, and that Emacs held 82 open on an SMB share, file notification's watches of the Org files it visits there. A small program holding the same 82 descriptors close-on-exec saw =posix_spawn= take up to 2.3 s; holding them without close-on-exec, or holding the 24 local ones, never more than 3 ms. How long depends on how the share answers at that moment, which is why the freezes came and went.

So requests no longer start a process: =opencode-transport-request= speaks HTTP/1.1 over sockets Emacs opens itself with =make-network-process=, which opens them without waiting, and reads answers as they arrive, however reads split them, framed by Content-Length, by chunks, or by the end of the connection. A connection whose answer completed is kept for the next request to the same service, four at most, for a second less than the service's announced keep-alive timeout, five seconds for Node's server; a request sent on a kept connection that the service closed before any answer is sent once more on a new one, which is the race keeping connections brings, and a retry after looking for the service again always takes a new one. Failures carry a reason, which =opencode-request= retries on as it did on curl's exits: =refused= and =closed= after looking for the service, a 401 after rereading the registration. The stream is a request whose body never ends, read by a filter; =opencode-transport-cancel= ends it. Against the fake service in a batch Emacs, a request was answered after 0.27 ms at the median and 0.56 ms at the 99th percentile, against 19.8 and 24.6 ms with curl, the call itself taking 0.08 ms rather than 0.8 ms; fifty at once, after 8.6 ms against 112 ms. With the 82 watches of the share, the call to send one took 0.39 ms at most, against 58 ms with curl.

* Several services

Emacs may talk to several OpenCode services at once: the local one, found and started as above, and remote ones, such as another host's, which drover reaches through its peer link. A remote service is registered by name with =opencode-service-register=, given a function telling how to reach it, a connection plist whose URL is an http one or a relay's, =relay://NAME=, and is never started, restarted nor stopped by Emacs; =opencode-service-unregister= closes it.

** What a service keeps, and where

Everything the modules kept once for the one service is kept per service: the lookup and its waiters, the event stream with its queue, backoff and watchdog, the registry, the catalogs and the locations found missing, the catch-ups after a reconnection, the session buffers by ID, the projects last fetched, the subagent requests to propagate, the mode lines to update. Each such variable is declared with =opencode-defvar-service= and read with =opencode-sv=, a place. The local service keeps its values in the variables themselves, as before services existed; a remote service keeps them in a table of its own (=opencode--service-states=), made fresh from each variable's initial value on first use. So code and tests reading the variables directly, such as drover's =opencode-session-buffers= lookups, see the local service's, and loading this version into an Emacs running an earlier one keeps the live state where it is: the registry, the open stream and the session buffers are the local service's, its timers and the closures of requests in flight still read and write the variables they did, which are the local service's storage. Nothing is migrated.

| Considered                                                     | Chosen? | Why                                                                                                                                                                                                                                                                                                                                       |
|----------------------------------------------------------------+---------+-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| The variables the local service's storage, a table per remote | yes     | the local service unchanged, in its code paths, its costs and its tests; a running Emacs loads it without migrating anything, closures of the earlier version included                                                                                                                                                                  |
| A service object holding all the state, every reader changed  | no      | about 600 references rewritten, and a running Emacs's closures and timers made by the earlier version would write to variables nothing reads any more: a stream reopening, whose closure clears the flag that it is opening, would never reopen                                                                                          |
| The variables swapped for a remote service's values while its code runs, by dynamic binding | no | values set during the binding must be saved back as it ends, nested bindings of two services fight over them, and anything running within the binding while it waits, timers and filters of the other service and of other packages, sees the wrong service's state |

** Which service code works for

=opencode-current-service= is the service bound by =opencode-with-service=, else the current buffer's when it is a session buffer of a remote service (=opencode--buffer-service=, permanent so that the mode keeps it), else the local service. Every timer, request callback, stream filter and event dispatch of a service's machinery binds its service, the local one included, since a timer runs in whatever buffer is current, and the user's may be a remote session buffer: a function a timer runs takes its service as its last optional argument, given only for a remote service (=opencode--timer-arguments=), so that the local service's timers, and the tests holding them, run as before; a closure captures it. =opencode-request= captures the current service and binds it around THEN and ELSE. The mode line, a session buffer's =kill-buffer-hook= functions and the global window hooks bind the buffer's own service, since redisplay and hooks may run within another's binding. Commands need nothing: run in a remote session buffer, they find its service through the buffer; that is why the buffer counts at all.

Hooks opencode.el runs for a service, =opencode-state-updated-functions=, =opencode-session-buffer-functions=, =opencode-catalog-changed-functions=, the event handlers of =opencode-events-register= and the others, run with that service bound: their functions read its registry and catalogs. A package following only the local service checks =opencode-service-remote-p= there and leaves; one reading the registry from timers or commands that may run in a remote session buffer binds the local service, =(opencode-with-service nil ...)=, as drover's OpenCode backend does.

** A remote service

| What                       | Local service                                    | Remote service                                                                                                                                                                                       |
|----------------------------+--------------------------------------------------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Finding it                 | the registration file, the CLI to start it       | its function, asked again whenever it cannot be reached or refuses the password; =/api/info= must answer; nothing imported is waited for, no version compared with the CLI                           |
| Its event stream           | wanted while buffers are open or the registry has clients | wanted while its buffers are open; its own backoff, watchdog and queue, dispatched from its own timer                                                                                       |
| Its registry               | every unarchived session, listed a page at a time | the sessions of its buffers, the running ones, their subagents and the sessions above them, fetched by ID, never listed: an event of another session is not followed, and one changing a status has it fetched once, kept only when related (=opencode-state--followed-p=) |
| Directories                | resolved through the file system                 | spelled as that service spells them, backslashes made slashes and a drive letter upcased, never resolved (=opencode--remote-directory=)                                                              |
| A session buffer           | in its session's directory                       | named =*OpenCode@Core: Title*=, in this host's home, its session's directory in =opencode-session-location=; requests made there are scoped to it (=opencode-location=)                                |
| Files                      | linked, visited, processed after edits, attached by reference | its host's: none links nor resolves, nothing processes edits, the desktop does not save the buffer; this host's files attach inline, as data, its host's by reference, found through =/api/fs/find= |
| Notifications, mode line   | as ever                                          | the host named: =Core: Title= in the mode line, =(Core)= after a notification's title                                                                                                                |
| Restart, stop              | =opencode-service-restart=, =opencode-service-stop= | never: those commands act on the local service whatever buffer they run in                                                                                                                        |

Unregistered, a service's stream closes, its waiting requests fail, its timers stop, and its buffers stay, their header line saying they no longer follow their sessions; registered again under its name, it is the same service, its buffers following it anew as its stream reopens.

** Relays

A relay carries the requests of its URLs over a link of its own: =opencode-transport-request= hands a request of =relay://NAME/...= to the function registered as NAME, with its method, path, headers and body, and the function answers with =opencode-transport-relay-answer=, or feeds a stream with =opencode-transport-relay-chunk= and ends it with =opencode-transport-relay-end=, or fails it with =opencode-transport-relay-fail=; the request settles once, times out and is cancelled as any other, its cancellation reaching the relay. Everything above the transport is unchanged: probes, requests and the event stream reach a relayed service as they reach an HTTP one. drover's relay carries them to another host's drover, which performs them against its own service with its own credentials, so that the password never leaves that host.

** Tests

=test/opencode-services-test.el= runs two fake services at once, each a server of its own: the remote one reached directly and through a relay adding the password the requests lack. One session ID open on both is two buffers, named apart; requests go to their service, scoped to the directory as that host spells it; each stream's events reach its own buffers, whatever buffer is current while they are dispatched; registries and catalogs are kept apart, the remote registry holding its buffer's session, the running one and a subagent created, not the others nor any listing; the remote service's streams dropping leave the local one's alone and come back alone; gone for good, its requests fail while the local service's succeed; unregistered and registered again, its buffers follow it anew; its files neither resolve nor are processed, this host's attach inline and its host's by reference; its host is named in the mode line and in notifications.

* Tests

Tests run only in a separate =emacs -Q=: they never evaluate anything in a running session or talk to a real service. Fixtures under =test/fixtures/v2= were recorded from a service driving scripted sessions in a scratch repository and sanitized of paths and account identifiers. Session tests answer requests synchronously from route handlers. Transport tests talk HTTP over sockets to a local server registered in a temporary =service.json=, which keeps connections open as Node's server does, and can answer in chunks and a few bytes at a time; the parser is also checked on answers cut at every byte. One listening process serves the whole run, because on Windows a server created after earlier ones were deleted stops accepting connections after a few. Batch Emacs formats every mode line as an empty string, so the one rendering test is tagged =gui= and runs under =make test-gui=. The route handlers keep a fake inbox per session from the inbox events tests dispatch, which the inbox route lists, so that reloads and catch-ups find what the service would. Likewise, a turn run against the fake service is in its transcript before its events go out, as the service appends a message before the event naming it: with a transcript lagging the events, a test passed or failed as a catch-up came before the reply's events or after them, which only the order of answers decided. Each test's fake service starts a new world, whose first stream is the first Emacs opened, whatever tests ran before. The fake service accepts what it is sent, so =make contract= records every request the tests make and checks its route, query and body against the API document of an OpenCode checkout: those that session tests answer without a connection as =opencode-request= would send them, and those that reach the fake service as they arrive, so that what the HTTP client puts on the wire is checked too.
