* The server is authoritative

Buffers render what the service reports and keep only interface state: which blocks are expanded, the prompt being typed, pending answers. Agent, model, variant, status and transcript come from the service, so another client's actions show up in Emacs and nothing needs reconciling beyond what reconnection does.

* One service, one stream

OpenCode 2 runs one background service per user. Emacs never starts a server of its own and never stops the service: the TUI and the desktop app share it, and it resumes running turns after a restart. Every location's events arrive on a single =GET /api/event= stream. The process filter only splits frames and queues them, and a zero-delay timer dispatches them in time-bounded batches, because the service drops a subscriber that falls 4096 frames behind and a slow handler must not stall the socket. Frame scanning resumes where the previous chunk ended, so a multi-megabyte tool result costs linear time. Nothing is replayed after a reconnect: =server.connected= has every open buffer catch up with the service, writing only what it missed (see [[*Catching up after a reconnection][Catching up after a reconnection]]).

Locations are keyed by the exact directory string the service receives, so every directory is normalized the same way: truename, trailing slash, and an uppercase drive letter on Windows.

Whatever stops the service, Emacs restarting or stopping it, another client, a crash, the next request starts it again: a refused connection is retried once after =opencode-service-ensure= found or started a service. While Emacs runs =opencode service restart= or =stop=, requests wait for the CLI to end, then for a ready service, rather than reach the service going away or run =opencode service start= beside the CLI: every lookup is numbered, and a restart or stop numbers a new one, so that a lookup in flight, which may have found the service going away, settles nothing.

The stream must come back as soon as the service does, or replies stop rendering while prompts still go through. It reopens after a backoff when it ends, and at once, without backoff, whenever a service is ready for Emacs: after any start, restart or lookup Emacs made, such as the one following a request refused by a service that went away. One still open on another service process moves to the ready one. A sent prompt, command or shell command reopens it at once too, and the heartbeat watchdog reopens a wanted stream left closed with nothing reopening it, so that no lost notification leaves buffers stale. =opencode-service-stop= closes it and keeps it closed, since reopening it would start the service again; a service ready again reopens it only while session buffers are open or the registry has clients (=opencode-events-wanted-functions=). =opencode-disconnect= alone keeps it closed until a client connects.

The watchdog drops a stream that sent nothing, not even its heartbeat every 15 seconds, for =opencode-events-heartbeat-timeout= seconds. Emacs reads no output while the machine sleeps, nor while it is busy, so silence then is no evidence: dropping the stream on waking cost a healthy stream a reconnection, and every buffer a resynchronization. The watchdog checks every 15 seconds, and a check coming more than one interval late, or finding the clock set back, means it could not watch meanwhile: the silence then counts from that check, which gives the stream a whole timeout to deliver a heartbeat. A stream that died meanwhile is dropped once that timeout passed, as one dying while Emacs watches is. Comparing a check with the previous one rather than reading the timer's schedule also covers Emacs's catching up on a late repeating timer, which runs it several times in a row: only the first of them is late.

Every asynchronous request goes through =opencode-plz=, which settles it exactly once and kills its curl buffer however it ends. =plz= calls back and kills the buffer only on the curl exits it recognizes, worded as on GNU/Linux: on macOS, a curl process killed by a signal, deleted by Emacs, its buffer killed or signaled from outside, reports =killed: 9= and ends without a callback, and so does one whose =:as= function signals. Every stream the watchdog dropped thus left a buffer behind, and a stream killed otherwise was never reopened. =opencode-plz= lets =plz= answer, from a timer due after =plz='s, and otherwise calls ELSE with the reason and kills the buffer itself.

A service starting on a database from OpenCode 1 imports that history in the background while it already answers, and it answers 404 for a session the import has yet to reach. So ready means imported: =opencode-service-ensure= polls =/api/experimental/migration/v1= once per service process before it settles its waiters, and no request can mistake a session not imported yet for a deleted one. A failed or stalled import is reported and then left behind, since the service is usable without it.

* One registry of session state

Session buffers know only their own session, so pickers and other packages' lists and dashboards read the registry in =opencode-state.el= instead: one entry per session, with its live state, independent of buffers. It holds what the service reports and derives the status from it; nothing is decided locally, so another client's actions show up and nothing needs reconciling beyond what a reconnection does.

Every time the stream connects, whoever opened it, the registry is rebuilt from REST: one page of the newest unarchived sessions, then the running ones, those older than the page fetched one by one, then the pending permission requests and forms of the running ones. The active list is fetched after the page, so a turn that ended in between shows as ended rather than running forever. Nothing is replayed after a reconnect, so events received before the requests are covered by their answers, and those received while they run are held and applied over the result. The registry is then ready and follows events. An event of a session whose entry is not current on this stream, unknown or left from the previous stream, fetches that session first, holding its events meanwhile.

The registry holds every unarchived session, not only the newest: lists such as drover's show the user's own sessions, and with many subagents, which are sessions too, a fixed number of the newest left out older top-level sessions still open in buffers. A service holds thousands (one had 2510 unarchived, 967 of them top-level), and one unpaged listing of them is 1.4 MB of JSON, so after the ready page the others are listed a page of 250 at a time, newest first, one request after the other, each page parsed and installed as it arrives: with Emacs 31's parser, a page costs about 0.6 ms to parse and as much to install, and allocates about 0.8 MB, so the main thread is never held for more than a page and a garbage collection. =session.list= has no maximum page size; its cursor anchors on the last session's update time and ID, and carries the first page's filters and order, so later pages send the cursor and the size alone. A session updated during the listing moves ahead of the first page, where later pages never find it; events the registry follows fetch such a session themselves, and for any other update the listing ends by following the first page's =previous= cursor, which lists the sessions newer than it. A page only installs the sessions the registry holds no current entry of: one an event fetched or changed since is newer, and one deleted meanwhile stays deleted. Sessions of a later page are not running, since the running ones came with the ready page, and only the failure of one whose failure is still unseen has its message fetched, the status showing it; so loading them all costs a request per page, not per session. A page that fails is asked again after a backoff, the registry staying ready. Clients hear of each page once: =opencode-state-updated-functions= runs once per batch, with nil when several sessions changed, while status changes are still reported one by one. Entries are found by ID in a hash table, and the 2510 sessions take about 3 MB.

The service archives a session alone: its subagents stay unarchived, listed while their parent is not, so the registry held subagents whose parent it did not know, and a list such as drover's could not tell the parent archived from deleted or not loaded; it showed them at the top of trees of their own. The registry now holds the sessions above those it holds, at any depth (=opencode-state--parents-wanted=): once the listing ends, the parents it lacks are fetched, archived ones included, with those the previous stream held kept until fetched again rather than dropped and fetched anew, and once loaded, a session fetched has its parent fetched in turn when missing. A parent deleted answers 404 and is let go. Archived parents are entries as any other, which =opencode-state-sessions= leaves out unless asked for archived ones; one whose subagents are gone is let go at the next rebuild. It costs a request per such parent, of which there are few.

A rebuild keeps the previous stream's entries until the listing ends, so lists do not empty while it runs, but treats none as current. When it ends, the entries the service no longer listed are dropped, except those of sessions open in a buffer, which are fetched: a session with a buffer always stays in the registry, archived or older than =opencode-state-recent-limit=, and =opencode-state-sessions= lists it even archived. A buffer opening after the listing fetches its session when the registry lacks it. =opencode-state-recent-limit= is now nil, all, by default; a number still caps the sessions listed, as it once set how many the single page held.

The service does not record when an execution started, nor when it asked a request it lists. A running turn's start is taken as the first message after the transcript's last idle marker, skipping agent, model and location switches, which happen between turns; a request's time comes from its ID, whose first 48 bits are the creation time in the service's ID layout, and a request the registry already knew keeps the time it had.

Unread is the service's, shared by every client: a session is unread when its idle time is newer than its viewed watermark. The registry projects both as the service does: an end of execution sets the idle time to the later of the event's time and one millisecond past the previous idle time, and an interruption by the service shutting down changes neither, since the restarted service resumes the turn. An entry fetched after an event may already reflect it, so a held or queued end of execution is not counted again when the entry's idle time already reaches the event's: counted twice, the idle time would run one millisecond ahead of the service's, which ignores a view of an idle time newer than its own, and the session would stay unread. Posting the view only when unread, and once per watermark while it is in flight, keeps the selection hooks from flooding the service.

Prompt-cache expiries, which only my fork reports, are kept apart from the entries, in a table of their own: the service lists them for every session with a live cache entry, the registry's or not, archived sessions included. They are listed whenever the stream connects, alongside the bootstrap; =session.cache.updated= then carries each session's new expiry after every provider response, and events received while a listing is in flight are held and applied over its answer, which may predate them. Nothing reports an entry running out, and once one has, a longer-lived entry of a shorter prefix may still serve the session (a system prompt cached for an hour under a conversation cached for five minutes), or a fork may have refreshed its parent's entry without an event to the parent; so one timer, set a second past the earliest known expiry, forgets the expiries that passed and lists them all again. A listing supersedes the one in flight, and the timer only ever waits for an expiry still ahead, so listings never loop. A service without the route answers an untagged 404: it then has no expiries, and is not asked again until the stream reconnects, maybe to a newer build; any other failure keeps the expiries known until the next one passes. An expiry names the tokens its entry covers and, from newer builds of the fork, =promptTokens=, the whole prompt of the session's last request, kept as =:prompt-tokens= so that lists can tell what share of the conversation a next turn would read from the cache; an older build leaves it nil.

Each entry carries the session's context size, as the session buffer counts it: the token counts, input, output, reasoning and cache reads and writes, of its newest assistant message reporting usage (=opencode-context-size= is that rule, for both). The end of every step reports it, and so does a step failing after the provider answered, whose message keeps that usage; the buffer notes both, so that streaming a turn leaves the size replaying it finds. Neither a session's info nor the session list has it, and no route lists it for several sessions: =session.tokens= sums every step, and the fork's cache listing covers only live cache entries. The cheapest source is the session's newest assistant message, =GET /api/session/:id/message?type=assistant&order=desc&limit=1=, the next one only when that step still runs or failed before the provider answered. Fetching it for every session the bootstrap loads would cost one request per session, thousands, on every reconnection, and each answer holds a whole step with its tool outputs; most of those sessions are never displayed. So the size is fetched only when a client asks for it (=opencode-state-context=), from a timer since clients ask at redisplay, which also lets one redisplay's asks queue up, coalesced per session, a few at a time (=opencode-state-context-requests=), in the order asked. A session the registry saw created starts with none known to be needed, and the end of a step settles a size without a request.

A compaction replaces the conversation, and nothing measures what it left until the next step ends; a manual compaction leaves the session idle, so that may take long. The compaction's own usage is no answer: it is that of its request, which read the conversation it replaced, and it sums every call the compaction made. My fork reports, on =session.compaction.ended= and on the completed compaction message, =context=, the service's estimate of the next request: system prompt, tools, the summary with the messages it keeps verbatim, and what followed, as the service estimates a request no step measured yet. A completed compaction settles the size to that estimate, marked =:context-estimated= in the entry and =opencode-session-tokens-estimated= in the buffer, until a step reports usage; without one, from a native compaction, whose encrypted window cannot be measured, or another service, the size is unknown until then, which is what OpenCode's own clients show after any compaction. Fetched, the size is that of the newer of the newest assistant message reporting usage and the newest completed compaction, the order replaying the transcript follows: compactions are paged from the newest, =type=compaction=, until a completed one or one older than that message. Messages are created as they are appended, so their creation times order them as the transcript does; a manual compaction's message has the ID of its =/compact= request, made before steps that ran while it waited, so IDs do not.

A fetch in flight is superseded by an event settling the size meanwhile, which is at least as recent as its answer, and by a committed revert, which removes messages the answer may still count; the revert also forgets the size, which is fetched again when asked for, as the buffer reloads its transcript then. A reconnection may have missed steps, and the service updates a session whenever a step ends or a revert is committed, but not when a compaction ends. So a size known when the stream dropped is only carried: once a fresh entry, from a page of the listing or a fetch, replaces its session's, the size stays only while the service's update time is not past the old entry's, and with it its estimate mark; a size settled since the rebuild began, by an event or a fetch, stays whatever the page holds, being newer. A session seen to start a compaction and not to end or fail it keeps no size across a rebuild: it is forgotten as the rebuild begins, rather than shown until the session's page arrives, and fetched again when asked for, until a fetch begun since finds no compaction running; the mark goes with the entry when the listing drops it. Fetches queued or in flight are queued again, since their answers belong to the stream that dropped. A failed fetch is not retried on every redisplay, only once the stream reconnects and a client asks again. Sessions the registry does not hold, such as archived ones drover lists from =opencode-fetch-sessions=, have no size: there is no entry to keep current, nor events to follow.

* Displays without a buffer

The session mode line's details are functions of an agent, a model reference, a token count and a directory, in =opencode-display.el=, so that other packages' lists show every session's agent, model, provider, variant and context as the mode line does, from the registry rather than a buffer: the mode line draws its agent with =opencode-agent-display= itself, so that a list's agent has its name, weight and colour. They read the location's cached catalogs and never wait, being called at redisplay: a value needing a catalog not fetched yet is nil, and the fetch is queued, once per catalog however many displays asked, and started from a timer, at most =opencode-catalog-requests= at a time, those not cached before those being renewed; =opencode-catalog-changed-functions= run when it arrives. A selected variant needs no catalog; a default one needs both the model and the provider catalogs, as the request it reproduces merges their settings. The mode line falls back to the agent, model and provider IDs until the catalogs arrive, as it always did.

A reconnection used to forget every catalog, since the service may have restarted with another configuration. With 53 locations in use, that refetched 114 catalogs after every reconnection, waking from sleep included, and each arrival forced every mode line of every frame to be redrawn: with 22 frames and 25 windows a forced redraw costs about 40 ms, so a reconnection held the main thread for seconds. Catalogs almost never change across a reconnection, so they are now stale while revalidated: the stream's opening marks every cached catalog stale, displays keep showing it, and the first display asking for one again queues its fetch, so that only the catalogs in use are fetched, and only on demand. An answer equal to the cached catalog changes nothing: no hook runs, no generation grows, nothing is redrawn. A command fetching a catalog (=opencode-catalog-fetch=, =opencode-catalog-wait=) gets a stale one renewed first, since it acts on the service's current configuration. An event saying a catalog changed (=agent.updated=, =model.updated=, =provider.updated=, =integration.updated=, =command.updated=) marks it stale and fetches it at once, without waiting for a display to ask; a fetch running then may answer from before the change, so another follows it, and an answer to a request begun before the stream reopened stays stale. A fetch that failed is not retried by displays, which ask at every redisplay, until the stream reopens or an event says the catalog changed.

A catalog that changed bumps =opencode-catalog-generation= and its location's count, =opencode-catalog-location-generation=, and updates only the mode lines of that location's session buffers shown in a window, with =force-mode-line-update= in each, from a zero-delay timer, so that any number of arrivals in one tick costs one pass. The mode line's segments are keyed on their location's count rather than the global one, so that a catalog arriving for another location recomputes nothing, and on the count of stream openings, so that a session buffer's mode line asks for its stale catalogs again once after a reconnection, when its resynchronization redraws it.

A session may live in a directory deleted since, such as a scratch worktree, and the service answers its location's requests 404 =LocationNotFoundError=. Displays ask for a missing catalog at every redisplay, and a failed fetch was reported for every catalog of every such location, in the echo area and =*Messages*=, and again after every reconnection, which forgot the failure. Such a failure now marks the location missing (=opencode-location-missing-p=): its catalogs count as cached and empty for displays, which show identifiers, as for a model a catalog lacks, rather than nothing; no display asks for them again; the absence is logged once per location, out of the echo area; and =opencode-catalog-changed-functions= run once, so that lists redraw with the identifiers. A reconnection marks the location to be checked once more, displays showing identifiers meanwhile rather than flickering to nothing, and an event of the location, or any answer from it, brings its catalogs back. A command asking for a catalog hears of the failure, as of any other.

* One look

The session mode line, the pickers and drover's lists showed sessions each their own way: the mode line a check mark for an idle session and a timer for a working one, in faces of its own, the pickers the same icons in other faces, drover a third set of faces, and its own options for the same icons, animations, agent faces, efforts, context and prompt-cache bars, and number formats.  A change to one look was a change to three, and they drifted: drover's waiting icon was gold, opencode.el's orange.  =opencode-look.el= now holds every one of them, and drover requires it and uses it for the sessions of every backend; its former options and faces are obsolete aliases of these, so that customizations of either keep working.

Where definitions differed, one was kept: drover's icons, animations, number formats and context wording, which the list the user reads most showed; opencode.el's faces where its colour roles mattered, the waiting status inheriting =opencode-attention=, as anything waiting on the user does, rather than =warning=, which themes may give the colour of other roles, and a retrying status in the working face, italic.  An entry of =opencode-session-status-icons= in its former form, (STATUS ICON FACE), still gives its icon: the faces are the statuses' own now.  The pickers title a session in the face of where it is in Emacs, as drover's lists do (=opencode-session-place=), and show the archive's icon; they leave idle titles undimmed, which in a minibuffer of mostly idle sessions would dim most candidates.

* An animated status

A working or retrying session's icon turns through the frames of =opencode-session-status-animations=, every =opencode-session-status-animation-interval= seconds, in the mode line as in drover's lists.  The frame shown comes from the clock (=opencode-session-status-frame-index=), so that every animated icon shows the same frame at the same time, and timers tick in the middle of a frame (=opencode-session-status-frame-delay=), so that one running a little late or early neither shows a frame twice nor skips one.

Emacs has no way from Lisp to redraw one window's mode line alone: =force-mode-line-update= redraws those of the windows showing the current buffer, and with ALL every mode line of every frame, which costs about 30 ms with 22 frames.  So one timer, for every session buffer, forces the mode lines of the buffers drawn animated last, and only those a window of a visible frame shows; a mode line drawn animated asks for the timer, which drops a buffer no longer shown or no longer animated, and stops when none is left, or when the pace changed, the mode lines then drawn starting it anew.  Nothing ticks while no animated icon shows.  Every frame is padded to the room of the widest frame or still icon, measured in the mode line's face, and the mode line is fitted with the still string: a frame changing fits nothing again, and only the tab, already made at every call, takes the new frame.

What the registry tells changes the icon without the buffer changing: a turn ended unseen, a subagent at work, the archive.  The registry keeps each session's subagents (=opencode-state--children=), as entries are stored, so that what a session's subagents do costs its subagents rather than every entry, and counts its changes (=opencode-state--revision=), until which the part of the mode line taken from it is kept.  A change of the registry compares, after the tick, that part for each session buffer shown, and updates only the mode lines it changed.

=dev/bench/run.sh= with =BENCH_RECONNECTS=0= measures it in the scene of [[*Mode lines at redisplay][Mode lines at redisplay]]: 22 frames, 25 windows, 26 session buffers with long transcripts, moody and minions.  With one animated window, a tick costs 8 µs of Lisp, the mode line it redraws 38 µs, and the redisplay it causes 3.0 ms, against 0.26 ms for a redisplay changing nothing; with the 24 session windows of 21 frames all animated, a tick costs 0.16 ms of Lisp, 24 mode lines 0.97 ms, 40 µs each, and the redisplay 29 ms, what forcing every mode line costs.  Left alone for 3 s, the timer ticked 20 times, 6.7 a second, the main thread never held more than 16 ms with one animated window, 41 ms with 24.  Most of a tick is Emacs redisplaying the windows of the buffers forced, which a buffer's mode line forced re-lays out without its usual shortcuts; it grows with the windows animated, not with the frames.

* Mode lines at redisplay

A session's mode line is computed again whenever its window's is redrawn: on every streamed chunk, whenever a window changes, and for every window whenever anything asks for all mode lines. Its Lisp cost was about 0.3 ms, mostly measuring and fitting the details. It is now cached at three levels: the segments, keyed on what they show as above; the details at every level with their pixel widths, keyed on the segments and the mode-line font; and, per window, the fitted title and details, keyed on the status icon, the segments, the buffer name, the window's width, the font, the mode-line height, whether moody is in use, and the rest of the mode line. The rest can change at any time, through minor modes, =global-mode-string= or another package, and only its text with its properties tells, so it is formatted at every call and compared with what the cached fit saw; that formatting is most of what remains, about 0.1 ms with moody and minions. The status is made again only when the pending requests, the status, the retry, the registry's part (see [[*An animated status][An animated status]]) or the look's options change, and the adapted format only when the default format or =mode-line-modes= change, compared by value since packages change them in place. The moody tab is drawn at every call, as moody draws the selected window's differently.

Emacs's default process filter has every mode line of every frame redrawn after each chunk of output it inserts, which made each request answered cost a forced redraw of all of them, hundreds over a reconnection. Requests never show their buffer, so =opencode-plz= inserts their output with a filter of its own, which redraws nothing.

=dev/bench/run.sh= measures this in a graphical =emacs -Q= dressed as a heavy user's: FiraCode Nerd Font, the tron-legacy theme, moody and minions, 22 frames and 25 windows showing session buffers of distinct locations, and a list drawing all 120 sessions of 53 locations with the displays, redrawn 0.1 s after the registry or a catalog changed, as drover does. The fake service runs in a batch Emacs of its own with the recorded catalogs, the model catalog five times its size. It reports, for the first load and for each reconnection, the time from =server.connected= until nothing was in flight for two seconds, the longest gap between ticks of a 10 ms timer, the time spent in gaps over 50 ms, the forced and targeted mode-line updates, the catalog requests and announcements, and the calls of =opencode-mode-line= with their cost; then the cost of a redisplay, unforced and with every mode line forced. Over two runs of three reconnections each:

A redisplay changing nothing costs 0.1 ms throughout, and one forcing every mode line 38 to 41 ms before, 29 to 35 ms after: Emacs's own share is most of it. The Lisp time of a session mode line whose inputs did not change fell from 285 to 320 µs to 76 to 138 µs, most of what remains formatting the rest of the mode line. The list is not redrawn at a reconnection, since the registry finds nothing changed, so only the session buffers' catalogs are renewed; a list redrawn then, as drover's is after its own reconnection requests, renews those it shows too, four at a time, redrawing nothing when they are unchanged. The benchmark has since grown into the one of [[*Catching up after a reconnection][Catching up after a reconnection]], whose sessions change while the stream is down.

* No session list

opencode.el has no session list buffer. drover lists the sessions of every agent front end, this one's included, and one listing is maintained rather than two that drift apart: drover reads the registry, which holds every unarchived session, can fetch others, such as archived ones, with =opencode-fetch-sessions=, names projects with =opencode-fetch-projects=, =opencode-project-for-directory= and =opencode-project-name=, and shows branches from =opencode-git-branch=. What opencode.el keeps is completion: =opencode= and the other pickers offer sessions in the minibuffer, and commands that act on a session pick one there when called outside a session buffer.

* Session pickers

Every picker goes through =opencode-annotated-completion=, with an affixation function. A session's status icon, and the archive's for an archived session, are the candidate's prefix and its project, branch and age the suffix, so neither is matched against the input nor sorted by: the candidate is the title alone, in the face of where the session is (see [[*One look][One look]]). Completion returns a string, so a title given twice gets =<2>=, =<3>= and so on, in display order, and every session stays reachable. The project and branch columns are padded to their widest value among the candidates, and a column no candidate has a value for is left out.

A picker receives session infos, fetched or kept in buffers and notifications, but shows what the registry knows when it holds the session: a buffer's info is not refreshed on every rename, move or turn, and only the registry knows that a turn runs. Projects name sessions only, so pickers name them from the projects last fetched rather than ask the service each time, and fetch them only when none were; a failure leaves the names out rather than the picker. Branches are read from HEAD, as =opencode-git-branch= does for drover.

Outside a session buffer, renaming, archiving, deleting and interrupting pick among the current project's sessions, those =opencode= offers: drover's lists act on any other. Interrupting offers only the sessions =/api/session/active= reports running, which holds whether or not the registry was bootstrapped.

* Live rendering equals replay

Opening a session renders its projected messages; afterwards the event stream drives the buffer. Both paths must produce the same text, which the tests check for every recorded scenario. That rule settled several choices:

- Text and reasoning fragments are keyed by assistant message and per-type ordinal (=MSG/t/N=, =MSG/r/N=), tool calls by call ID, so a late event finds its block wherever the stream left the cursor.
- Reasoning blocks are created on their first text, since encrypted reasoning arrives empty.
- A prompt sent from Emacs carries an ID generated locally, in the service's ID layout, so its echo on the stream is recognized and not rendered twice; prompts of other clients render when the inbox delivers them, where replay places them.
- A prompt typed here shows where it was typed, and its input gets its message ID, which revert and fork at point need, when the service delivers it: only then does the message exist, a steering prompt waiting for the next step and a queued one for the end of the turn. Markers keep the input while it waits, so output inserted meanwhile and several prompts waiting at once are no matter; a failed or cancelled prompt never gets the ID, and one whose input a reload erased renders on delivery like another client's.
- Typed while a turn streams, a prompt sits before output that precedes it in the conversation. Where the transcript ended at its delivery is recorded, and cuts order messages by it, so they follow the conversation, as replay renders it, rather than the buffer.
- A slash command's prompt gets an ID from the service, which only the stream reports, and text expanded from the command's template. The command carries a correlation key in its metadata, which the service passes on to that prompt, so its input gets the prompt's ID; the expanded prompt renders on delivery. A command run by a subagent prompts no message here, so the key is given up a minute after the command's request returned. A shell command makes no prompt: its shell message and result, like other messages between prompts, never start a cut.
- The package tracks its own prompt start marker: =comint-last-prompt= would count the last line of output as the prompt.
- Notices are inserted before the idle prompt, and a turn started elsewhere lifts the prompt first.
- A background job's completion is a synthetic message, keyed by its message ID, which its inbox item shares. Its metadata makes it a block of the job's tool, and the element wrapping its text is removed only when it is exactly what the service writes, so an unexpected text shows whole.

* Catching up after a reconnection

The service replays nothing to a stream that reconnects, so every open buffer must find what it missed. It used to compare its session's update time with the one it fetched when it opened, and render its whole transcript again when they differed or a turn ran. Events never refreshed that time, so every buffer whose session had run a turn since it opened rendered its whole transcript again at every reconnection. With 26 buffers open, some with thousands of parts, a reconnection held Emacs for 9.6 s in one stretch.

The live events tell which messages a buffer renders: the service names a message after the event appending it (=msg_= and the event ID's suffix), a prompt or note after its inbox item, a step after its =assistantMessageID=. So the buffer records the ID of each message it renders, from events and transcripts alike, and whether it is open, as a running step, shell command or compaction is, or finished. Whenever none is open, everything up to the newest message is rendered for good: that message and the end of the transcript, before the idle prompt, are where the buffer is in sync (=opencode--synced=, =opencode-synced-end=), with the state writing more needs, the kind of the last block, the errors shown in the turn and the start of the last answer. Expanding the block ending there writes at that point, which then moves after the expansion.

At a reconnection, every buffer fetches its session, adopting its location, title and selections, then the newest page of its messages, five of them, and pages of 25, 100 and 200 further back until one holds the message it is in sync with. Most buffers missed nothing, or a turn: the first page tells, and a buffer with nothing newer and nothing open writes nothing at all. Otherwise it deletes what follows its sync point, the step that was running included, and writes the messages after its sync message from the state saved there. As live rendering equals replay, that is what a buffer opened afresh shows. When the first page lacks that message, the service is asked whether it still has it: a revert or a fork-and-replace removed it, and the buffer renders its whole transcript again rather than page back through all of it. The status comes from the running sessions, asked once for every buffer.

Answers and events race: an event arriving while a buffer fetches may be in the answer already, or not. So a buffer withholds its session's events from the stream's reopening, and from the start of any whole load, until it has written what it fetched, then applies them in order, and nothing already rendered is rendered twice. An event appending a known message renders nothing; events of the parts of a finished step change nothing; a step still running in the answer has its finished parts noted as shown, and those still empty, whose deltas were missed, are shown whole when they end; a tool call never goes back from finished to running. A withheld end of a tool call shown finished already still runs the hooks of a finished call, as the call did end live, and the status is first set to the one before the first withheld turn event, so that applying them leaves the status they lead to.

Buffers shown in a window catch up first, =opencode-resync-requests= at a time. A reconnection during a catch-up abandons it and begins again; a buffer loading its whole transcript catches up once loaded, as its answer may predate the reconnection. Transcripts are written =opencode-replay-slice= seconds at a time from timers. While a buffer writes its whole transcript, its windows show its start between slices, which redisplay fontified already, rather than the newest text of every slice, tens of milliseconds a slice for a window of Markdown; they go back to its end once it is written. Summaries written meanwhile are fitted only where a window shows them, or will once redisplayed: fitting thousands after each slice cost tens of milliseconds, and those elsewhere are fitted when scrolled to.

=dev/bench/run.sh= now opens 26 session buffers in its graphical =emacs -Q= with the user's garbage collection thresholds (100 MiB, 0.5), 24 of them shown in 21 frames, three of them split, the list in the 22nd: four transcripts of 400 turns, eight of 60 and fourteen of 8, of six parts each (a prompt, reasoning, a file read, a shell command with its output, an answer in Markdown, with a table every seventh turn, and the turn's end), 2400 parts for the long ones. While the stream is down before each reconnection, the service adds a turn to half of the open sessions, the long ones included, and starts or ends a turn in another, which then runs at the reconnection; before the second, it also reverts a long session's last turn and replaces it, so that one buffer must render its whole transcript again. * Writing a transcript in linear time

Writing a transcript whole cost time quadratic in its length, which made a reconnection rendering a few long ones take seconds. Three causes stacked, which =opencode-test-replay-time-linear= now guards against: a transcript four times longer must take less than eight times as long.

The undo list keeps only the prompt's edits: an output change drops its records and shifts the prompt's by its length. Replaying a prompt runs Comint's input sending, whose records, made at the input, are not output; they were kept, two per prompt, and every later output change shifted all of them, which was the 1250 profiler samples of =opencode--undo-shift= at the user's reconnection. They also let undo rewrite the transcript. A transcript is now written under =opencode-without-undo=, which records nothing and shifts the prompt's records once afterwards, by how far the input moved; so is another client's prompt rendered live.

=comint-output-filter= makes three markers on every call, which stay in the buffer until a garbage collection, and every insertion adjusts every marker of the buffer. With the user's large =gc-cons-threshold=, tens of thousands accumulated while a transcript was written. Session buffers write with =opencode--output-filter= instead, which does exactly what Comint's does with markers it reuses, the prompt's included, and so does the idle prompt.

Rendering each table had set up =markdown-ts-mode= in a fresh buffer, which looks up every grammar: 8 ms a table, now 0.5 ms with one buffer set up once. Scanning a text block for its tables parses the transcript; a block without a pipe has none, and is no longer scanned. And a tool call's path is made relative to the project through true names, which stat every directory of both; the result is now cached. Byte-compiled, writing 1000 turns of four messages took 6.7 s, and four times as long for twice as many; it takes 0.1 s, and 4000 turns 0.37 s.

* Points that follow output

A point at the end of the transcript or in the input follows output, in the buffer and in every window showing it, selected or not; one elsewhere in the transcript keeps its text, and its window its start. The end of the transcript starts at the idle prompt when one is shown, whose markup is hidden, so that a point before it looks the same as one after it; otherwise at the process mark.

Comint provides this for the output it writes: the buffer's point is saved with a marker that advances, window points advance through =window-point-insertion-type=, and =comint-postoutput-scroll-to-bottom= moves window points left at the process mark after the output and scrolls their window to it. Output written otherwise needs the same care, which =opencode-keeping-followers= gives it: it records each following point by its distance from the end of the buffer, which writing, replacing or deleting transcript text leaves unchanged, and puts it back there afterwards. It wraps the expansions written at the process mark, tables aligned in place, which may also grow past the process mark (the process mark then moves after them, or their tail would become input), and table reflows. Nested calls leave the points to the outermost one, which saw them before anything changed: rewriting a block ending the output deletes it first, which brings the points that were in it to the process mark.

=opencode-call-preserving-viewport= wraps output that must not move what the user reads: the prompt shown when a turn ends, notices, other clients' prompts, permission fallbacks, question blocks, rewritten expansions. It keeps the following points so, which also keeps a point's place in an input that rendering another client's prompt lifts and puts back, and the others with markers that stay before what is written at them. Following windows are left to Comint and redisplay, as for streamed output.

Markers do not survive reloading, which erases the buffer: =opencode-save-viewport= records the following points by distance, the others by line and column, and their windows' starts by line, and =opencode-session-reload= puts them back once the transcript and the input are written again. A desktop entry marks a point that followed output, which then comes back at the end of a transcript that may have grown. A window takes the insertion type of its point from the buffer it is shown, so the windows showing a restored placeholder are shown the session buffer again once its mode is set, which also gives them its margins.

Batch Emacs has windows but never redisplays them, so the tests check window points and starts in real windows, through the event handlers, rather than what is visible.

* Fontification that survives

Markdown is fontified by =markdown-ts-mode= as text streams in. Regions that must keep their own faces (verbatim output, tool summaries, buttons) are marked with properties the Markdown fontifier skips, and buttons are made after fontification from registered buttonizers. Font-lock also owns =display=, removing it at every fontification, so a renderer laying text out with it, as a table renderer pads a cell holding an emoji wider than two columns with a space a few pixels wide, records it with =opencode-keep-display= and every fontification puts it back. Half-typed Markdown never turns the transcript red: the parser's error feature is off.

Links are buttons made from output, never by font-lock, so that they are only ever in the transcript: =RET= on one follows it, while =RET= in the input sends it. A prompt, once sent, is part of the transcript too, though Comint writes it as input rather than as output: its links are made when it becomes sent text, in =opencode-highlight-input=, which marks every prompt sent from the input, written for another client or replayed, the reload and the catch-up included. Without them, =M-n= and =M-p= skipped a URL written out in a prompt, and =RET= on it, finding no button, took the prompt as old input and sent it again. markdown-ts also links URLs written out, at redisplay, in the input too, and opens them as mail; session buffers drop that, and the buttons it makes of the Markdown links typed in the input. A URL written out has no closing delimiter, so it becomes a button once a character that cannot continue it follows, or once the block writing it ends: a streamed URL is never a button of half its length. A link of another kind holding it, such as an Org link whose description arrives later, takes its place. URLs are links in code spans and blocks too, the link face added over the code's; in summaries they are not, as a summary is cut to fit and its keys toggle its block. Verbatim text loses the buttons Markdown makes in it at every fontification, so a durable button keeps its category, which gives it its keys, with its other properties, and the link face is a kind added to =verbatim= rather than one replacing it.

* Parsers that go with their text

markdown-ts parses each inline region, a paragraph, a list item or a heading's text, with a tree-sitter parser of its own: treesit.el keeps it in an overlay over the region (=treesit-parser=, =treesit-parser-local-p=), finds it again there when fontification updates the region's ranges, and deletes it only when such an update finds the overlay stale. Every change of the buffer's text edits every parser the buffer holds, and redisplay updates the ranges of every changed region, so a parser costs as long as it lives. Session buffers deleted the overlays holding parsers without deleting the parsers: reloading erased the buffer with =remove-overlays=, catching up deleted the overlays of the running step it wrote again, and lifting the prompt split, with =remove-overlays=, the overlay of an answer that had grown over the prompt and the input typed after it, leaving two overlays holding one parser, which two regions then shared. Each lost parser lived as long as the buffer, and its region was given another at its next fontification. A user's session buffer held 3221 parsers, 2793 of them without an overlay, and more every few minutes; creating parsers took 5.5% of the main thread, and querying their ranges allocated 53 MB in 250 s.

So the parsers go with their text. =opencode-delete-overlays=, which reloading, catching up and lifting the prompt use instead, deletes only the overlays lying within its region, never splitting one, and the parsers they hold. Text deleted any other way, a block collapsed or rewritten, a summary replaced, a table aligned, a fallback line or the input deleted, has its parsers deleted by change hooks: the parsers whose overlays lie within the text a change replaces are noted before it and deleted after it, when it changed the text rather than only its properties, which leave =buffer-chars-modified-tick= alone. A buffer that turns its change hooks off, as deleting an attachment's label does, calls =opencode-delete-parsers= itself. Killing a buffer frees its parsers with it.

Buffers set up by earlier versions keep their orphans until pruned: a parser no overlay holds, or only an empty one, is deleted, and so is an overlay holding a parser deleted already or one another overlay holds too. Each deletion walks the buffer's whole parser list, so a buffer prunes them by itself a slice of 30 ms at a time, from timers: the first time this version fontifies it, and whenever it reloads or catches up. =opencode-session-prune-parsers= prunes at once.

* Requests that wait

Permission requests and questions mark the block of the tool call that raised them and never take focus. A request whose block has not been inserted yet prints a fallback line that the block replaces. Requests of a subagent mark its block in the parent session. Answers from any client resolve them through =permission.replied= and =form.replied= or =form.cancelled=.

A request is answered in a transient, which remembers the request it shows (=opencode--active-form=, =opencode--active-permission=) so that an answer from elsewhere closes it, and which leaves a request pending when quit or suspended, from =transient-exit-hook=. That hook runs on the exit of any transient, and a transient opened by a suffix of another, such as drover's menu, is set up before that other one finishes exiting: its exit then comes once the request's transient shows, and counted as the request's own, it forgot the question it showed, whose next answer failed. So the exit counts only once the request's transient is no longer shown. A question can also be answered elsewhere while a suffix runs, such as while a custom answer is typed after the transient was left; the suffix then lets it go.

A list such as drover's answers in place: =opencode-respond-session= with IN-PLACE opens the transient from the selected window, without showing the session's buffer, which would take the user away from the list. The request's state stays in that buffer, opened or refreshed in the background when needed, so that the answer is posted and recorded exactly as when given there; the transient's state records that it is answered in place, since a question re-shows its transient from a timer for every question, after any dynamic binding ended. The context the transcript gives otherwise goes into the transient: a heading naming the session, and for a file permission the change asked for, which its block shows in the transcript. So the menu must show, whatever =transient-show-menu= says, and the keys scrolling the transcript scroll the menu when no window shows the session.

The service neither answers nor dismisses a request when a prompt arrives: it admits the prompt to the session's inbox, and delivers a steering one at the next step boundary, which a step waiting on its tool calls reaches only once the request is settled. A prompt sent then would wait unread, which looks like a lost =RET=, so a send check asks first, from the session buffer's requests, those of its subagents' buffers, and the registry's, which knows subagents without a buffer. Queued input, shell commands and sends without checks do not ask: their outcome is what was asked for.

* Keys

The package binds only what a Comint or special-mode user expects, plus =C-c C-o= to open links, as in Org, and the keys of its own transients, blocks, links and the desktop placeholder. Every other command is left unbound, so that one set of maps can cover several agent front ends: drover provides them, acting through functions that need no buffer (=opencode-session-delete=, =opencode-session-fork=, =opencode-session-compact=, =opencode-rename-session=) and commands that work from any key (=opencode-attach=, =opencode-mention-subagent=, =opencode-insert-slash-command=). The commands that edit the input act on the current buffer when it is a session buffer, and otherwise on the last selected one, since drover may run them in a session buffer that is not selected. =/= and =@= keep their electric meaning at the input, sharing the code of those commands; =opencode-insert-slash-command= puts a command at the start of the input from any key, the text already typed becoming its arguments, as typing =/= there does, and replaces a command the input already starts with rather than nest one in another's arguments.

Hints that name a command, in messages, notices and tooltips, go through =opencode-command-keys=, which asks =opencode-command-keys-function= for the keys first, since with few keys of its own =substitute-command-keys= would mostly find none; drover answers with its own. Comint refusals name the keys of what to do instead the same way.

A session buffer inherits =comint-mode-map=, whose keys show through once the package binds nothing over them. Its process is a pipe that runs nothing, so the commands meant for a subprocess are remapped, which keeps their keys and menu entries meaning what they mean in Comint: an OpenCode equivalent where there is one, else =opencode-comint-unsupported=, which refuses with the reason. Remapping rather than binding keeps the standard keys' standard meaning and covers the menus too. =revert-buffer= in a session buffer renders its transcript again.

Comint takes the input by deleting it and inserting it again as sent text, which deletes the labels of its attachments, and deleting a label drops its attachment. That deletion used to be spared only while =this-command= was =comint-send-input=, but =RET= runs =opencode-send-input=, and an input sent once its session left the archive is sent from a callback, where =this-command= is whatever command ran last: the labels' attachments were dropped and the prompt went without its files and mentions. Whatever sends the input through Comint now goes through =opencode--comint-send=, which binds =opencode--sending-input= to the buffer while Comint takes it, until =opencode--send-input= receives it; =comint-send-input= is remapped to =opencode-send-input=, so that any key bound to it does too. =M-x comint-send-input= finds no remapping, so =comint-send-input= is advised, as =cd= is: in a session buffer, a call without arguments made outside =opencode--comint-send= runs =opencode-send-input=, with its checks, the archive and the attachments, and a call with arguments lets Comint take the input with the flag bound, keeping a copy that a send check cancelling it puts back; elsewhere, and for the text a session buffer writes through Comint with another sender, such as another client's prompt, the advice only calls Comint. =opencode--comint-send= and a guard bound while =opencode-send-input= runs keep it from recursing. A label deleted by editing still drops its attachment.

Rendering lifts the input too: another client's prompt is written before it, which takes the input out and puts it back, and a transcript rendered again, on a reload or a catch-up that finds its sync point gone, erases it and writes it again. Both kept only the text: the attachments of a lifted input were dropped by the deletion, those of an erased one stayed with no label left to remove them by, and a label became plain text. Every path lifting the input now goes through one pair, =opencode--take-input= (=opencode--copy-input= with TAKE) and =opencode--put-back-input=: the input's text with its properties, its labels as offsets with their attachments and displays, and the next prompt's attachments, which leave =opencode--attachments= while the input is out, so that nothing is sent without its label meanwhile; the labels' overlays are deleted before the text, so that removing it drops nothing, and made again, with the hook removing an attachment, when the text is back. A transcript that cannot be loaded again puts the input back as well, rather than lose it with the failure.

Comint binds no =TAB=; Shell mode binds it to =completion-at-point=, and so does =opencode-tab-dwim= at the input, while the read-only transcript keeps =TAB= for its blocks and buttons. Comint's own completion function reads any word at point as a file name and is exclusive, so a word that names no file would fail before the global completion functions, such as a dabbrev function, are tried: session buffers call it through a wrapper making its file names non-exclusive.

* Edits only from live turns

Post-edit hooks run from =session.tool.success= of live turns only. A reloaded transcript or a fork is built from projected messages and never reruns them, so files edited long ago are never reformatted; the hooks also check that no transcript is being written, so that neither opening nor catching up ever processes a file. The diff an edit or patch reports gives the line ranges; a write reports none and counts as the whole file. Processing never asks anything: the service writes files behind Emacs, and a stale buffer would otherwise prompt whether to reread it.

Processing runs from events, in the background, so nothing it does may ask a question, which would take the user's minibuffer from a timer and hold Emacs until answered. Visiting a file runs its mode's hooks and applies its local variables, those of a =.dir-locals.el= included, and Emacs asks before applying risky ones: a session editing this very repository, whose =.dir-locals.el= then held a risky entry, opened that question in the middle of a reconnection. Processing now runs under =opencode-without-asking=: only safe local variables apply, nothing risky is offered, =inhibit-interaction= turns any question a mode hook, a lock or a save would ask into an error, which leaves the file alone with a message, and messages stay out of the echo area.

* The prompt cache

The cache guard's report comes from the service, which dry-runs the request the turn would send and compares it with what the provider confirmed it cached. The check runs from =RET=, before Comint takes the input, so declining leaves the prompt untouched; a caller that switches agent or model before sending passes them to the check, so no question appears from an asynchronous callback. Every prompt and command carries =thinkingLoss: "ask"= in its metadata, so the service refuses a turn that would replay stale thinking instead of letting the provider drop it, and consent sends =thinkingLoss: "accept"= on that one prompt. A service without the route answers an untagged 404, and the guard then stays off for it.

* Sending to an archived session

Input sent to an archived session brings it back from the archive first, wherever it comes from: =RET= and =opencode-queue-input= in its buffer, a slash or shell command typed there, =opencode-session-send= and =opencode-session-command=, which drover's prompts and scheduled deliveries use. The restore sits in front of the requests themselves, in =opencode--after-restore=, so no path can skip it. Whether a session is archived is read locally, from the registry, else from the session info of its buffer, which follows =session.archived= and =session.unarchived= for sessions the registry does not hold yet, such as one drover's archived view opened; a session that is not archived sends at once, as before, without a request more.

=RET= runs the send checks first, since they may ask, and a question cancelled must leave the session archived; only then is the session restored. The input waits at the prompt rather than be taken by Comint: a refused restore then sends nothing and leaves the input as typed, attachments included, and the notice saying why is all that changes. Once restored, the input is sent as if =RET= were pressed again where it was, with the delivery and the checks' metadata of the first press; =RET= meanwhile only says that it waits, so the checks do not ask twice.

One restore serves every send made while it runs: the sends wait in a list per session and go in the order they were made once the service answered, each in its buffer, or fail together with its error. The answer of =PATCH /api/session/:id= updates the registry and the buffer before they run, rather than leave them to the event, which may come later: a send made between the answer and the event would otherwise restore the session again. The event then changes nothing.

* Default variants

A model reference without a variant sends neither a variant's settings nor its body: the request carries what the provider and model catalog entries configure, and the provider decides the rest. The service never says which variant that amounts to, yet the mode line names it, so =opencode-model-default-variant= reproduces the request: the provider's settings with the model's merged over them, and the model's body overlay, read at the keys OpenCode's variants set; the OpenAI packages add a medium effort for GPT-5. Claude pairs every variant with adaptive thinking, so an effort counts only under it, and what the request leaves unset takes the API's defaults (=opencode-anthropic-default-efforts=), except behind Copilot, which handles Claude's effort itself; binding thinking blocks, from Claude 5.1 on unless the catalog says otherwise, turns adaptive thinking on. The variant named is the one sending the same effort, and none when no variant does.

* Tests

Tests run only in a separate =emacs -Q=: they never evaluate anything in a running session or talk to a real service. Fixtures under =test/fixtures/v2= were recorded from a service driving scripted sessions in a scratch repository and sanitized of paths and account identifiers. Session tests answer requests synchronously from route handlers. Transport tests talk HTTP through curl to a local server registered in a temporary =service.json=. One listening process serves the whole run, because on Windows a server created after earlier ones were deleted stops accepting connections after a few. Batch Emacs formats every mode line as an empty string, so the one rendering test is tagged =gui= and runs under =make test-gui=. The fake service accepts what it is sent, so =make contract= records every request the tests make and checks its route, query and body against the API document of an OpenCode checkout.
